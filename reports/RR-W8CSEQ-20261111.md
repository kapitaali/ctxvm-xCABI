## 2. Two review-side notes for the diagnostic (step 4), because the block (step 5) is built from it

The diagnostic is "one prompt per arm, read the real floor from the capture". A one-prompt run can and
cannot do this, and the difference matters because the **block's floor is the pair's budget** — the pair
is the expensive step (~20 minutes) and a wrong floor voids it.

**What a one-prompt-per-arm diagnostic CAN read (and should assert):**

- **The discriminating observable of the change: `page.fault == 0`.** In W8B, 19 of 21 pages faulted,
  because the text signal pinned nearly everything; with the text signal removed and the model reading
  each file once, the capture should carry **no** `page.fault` events. That single number *is* the change,
  measured — it is worth an explicit assertion in the diagnostic, because it is the difference between
  "the new instrument is in" and "the new instrument is in and no longer pins on prose". A fault here
  means the text signal is still pinning something, and the pair must not start.
- **The pinned block's size** (≈ 0 by the same measurement) and the **turn-0 residency**, which
  re-checks the system-prompt component (measured: 4,350 tokens from `turn.render.systemPromptBytes`).
- **The per-turn growth** in the new instrument (~4,700/turn measured on the W8B series), for the first
  step at least.

**What it CANNOT read: the floor itself.** The floor that binds is the *protected* set at the late
turns — system prompt + head 3 turns + tail 6 turns — and a one-prompt run never reaches the late turns,
so it cannot measure them. The floor therefore has to be **derived** from the measured W8B series
(10,518 → 104,032; ~4,700/turn): 4,350 + 3×4,700 + 6×4,700 + 2,000 = **48,650** ✓ (the plan's
arithmetic, re-derived here). The diagnostic's role is then to *verify the pins* and the growth, not to
measure the floor directly — the block states the derived floor, the measured growth, and the margin
above both, and the pair is the measurement that tests them.

**One bound the block should carry.** The plan's "turns above 60,000: 14–19" comes from the **pinned
ceiling** — the W8B series, in which 19 pins meant nothing was ever stubbed, so the measured residency
is an *upper bound* on what the new instrument would show. With the text signal gone, the policy stubs
eligible pages, so the new instrument's residency is **at or below** that ceiling and crosses 60,000
**no earlier** than turn 14 — the six-turn window is an **upper bound, not a promise**. The block should
therefore state the predicted eviction volume as a range (or state the bound explicitly), so that a
narrower window is not mistaken for a falsification. The falsifier itself is unaffected and remains
decidable: with the new signal and a floor-sized budget, zero evictions ⇒ the floor, not the signal, is
binding.

## 7. Erratum on this card's review note 1 — the fault count is NOT engine-side (their `f14db07`, verified
## in the observer's code)

Their `f14db07` ("W8C plan: the three review notes, and the fault number measured before trusting it")
takes notes 2 and 3 as they stand and **corrects note 1**. The correction is verified at the bytes it
cites, and it is right:

- **`page.fault` is emitted by the plugin OBSERVER, not by the engine.** `packages/hermes/src/plugin.py`
  has two fault rules: `tool_recall` (`:349-352` — a second declare of the same logicalRef with the same
  content hash, i.e. a re-read) and `identifier_scan` (`:426-434` — `scan()` over the model's produced
  text: if any identity token of a declared page appears in that text, a fault is emitted). The engine's
  pinning lives in a different module (`packages/hermes/live/context_engine.py`, `_credit_demand`).
- **The count is engine-independent, and the proof is in W8B's own data:** the *control* arm — which ran
  **no engine at all** (`context.engine: compressor`) — recorded the **same 19 faults** as the treatment.
  A count that is identical with and without the engine cannot measure the engine's pinning.

So this card's note 1 — "the diagnostic should assert `page.fault == 0`" — was **wrong in its
measurement choice**: removing the engine's `_credit_demand` would leave the 19 `identifier_scan` faults
in the capture untouched, so an assertion of zero faults would fail for a reason unrelated to the change.
**The discriminating observable is the engine's pin count by source** (which the plan's §4 already
requires: "the engine reports pins by source in its status"), i.e. `pins_by_source.text == 0` — not the
capture's fault count.

Two consequences worth carrying:

1. **The observer must be aligned in the same change, or the capture cannot be compared before/after.**
   Their plan now offers the two honest options — `scan()` stops emitting a fault for a prose mention
   (the mention becomes telemetry on the message) or the fault keeps its source and the assertion is
   `source == identifier_scan: 0` — and requires the alignment to happen in the same card, "or a
   diagnostic asserting zero faults would fail for an unrelated reason". Note the bookkeeping hazard if
   the observer is NOT aligned: the capture's fault count stays 19 after W8C, so a reader comparing W8B's
   and W8C's captures by fault count would conclude "nothing changed" — the before/after comparison must
   be on the engine's pin count, with the capture's fault count expected to be unchanged by design.
2. **My note 1 was right only *conditional on* that alignment.** With the observer aligned so that prose
   mentions are telemetry rather than faults, the capture's fault count does track the engine's
   re-read pins, and a zero-fault assertion becomes meaningful. Without it, it never is.

# RR-HELP-20261103 — the plugin can explain itself

**Card:** user request (2026-11-03). **Status:** landed; `ALL GATES GREEN`. Plugin **0.7.0**.

## 1. What was asked

1. `/ctxvm-help` — a short description of all the commands.
2. `/ctxvm-help <command>` — a longer description of one.
3. `/ctxvm-start` runnable **without parameters**, using the env defaults.
4. `/ctxvm-help environment` — the `CTXVM_*` variables and their values.

## 2. What landed

**`/ctxvm-help`** lists five commands with one usage line and one sentence each; **`/ctxvm-help
<command>`** prints usage, what the command changes, and the defaults it applies; an unknown topic
answers with the list of known ones instead of a bare error. `env`, `envvars` and `vars` are accepted
as short forms of `environment`.

**`/ctxvm-help environment`** prints, for each of the 17 `CTXVM_*` variables this plugin reads: the
current value, the fallback when unset (`unset -> on`, `unset -> 536870912`), and what the variable
changes. Above the table it prints whether capture is enabled and the resolved trace directory with
its source. A variable that is set to the empty string says `empty -> disabled` where that is the
meaning (capture, trace dir) rather than pretending to be unset.

**`/ctxvm-start [dir] [name]`** — no arguments is now the normal case. The directory is
`CTXVM_TRACE_DIR` when set, otherwise `${XDG_STATE_HOME:-~/.local/state}/ctxvm/traces` (created
0700); the name is `CTXVM_TRACE_NAME` when set, otherwise `<session-id>`. Arguments are overrides.
`/ctxvm-trace start` behaves identically, because it is the same handler.

**Source labelling, because a value without provenance is a trap.** The start/status output now says
where the directory came from: `slash command` for an argument, `env CTXVM_TRACE_DIR` for the
environment, `start (defaults)` for the fall-through.

## 3. Two defects found while building it

1. **A no-argument start silently discarded the env directory.** `_resolve_trace_dir(None)` returns
   the built-in default and never consults `CTXVM_TRACE_DIR`, so the first version of `/ctxvm-start`
   sent a configured operator to `~/.local/state` anyway. Fixed by reusing the directory already
   resolved for the process, and the test asserts the env path survives.
2. **The version number had never moved.** `PLUGIN_VERSION` and `plugin.yaml` were both `0.4.1`; the
   edits in the W15 and W14 cards searched for `0.4.0`, matched nothing, and reported success. Two
   reports and two commit messages therefore claimed 0.5.0 and 0.6.0 that never existed. Corrected in
   place in both reports, bumped to 0.7.0 here, and a test now asserts the constant and
   `plugin.yaml` agree — a bump that misses one file is a silent no-op, and the yaml is what the host
   displays.

Two existing tests had to be corrected rather than worked around: one captured "the last registered
command" and quietly started testing `/ctxvm-start` once three commands existed (it now looks the
command up by name), and the start test had to clear process state so the default path was genuinely
re-resolved instead of inherited.

## 5. Not claimed

- The help text is a static table in the adapter. It is honest about the commands that exist, but it
  cannot describe a command registered by a future plugin.
- `environment` prints values for this process only: the plugin reads its environment once at import,
  which the report and the command header both say. A change needs a gateway restart.

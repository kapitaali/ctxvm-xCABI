## What was done

- **Proof of the `06` §claim** *"hub.ctxvm.dev = Git repo + ODPC + Actions; no
  bespoke hub server"* — executed entirely with the open-data-products SDK
  0.4.0 in venv A (no venv B needed; ODPC building is ODPS-side):
  1. root manifest re-validated at build time (source gate)
  2. `odpc-build` over a staged copy of `04-odps-dataproduct-corpus.yaml` →
     `hub/catalog.yaml` (ODPC v1.0, `kind: Catalog`, metadata `hub.ctxvm.dev`,
     1 `productReferences` entry → ODPS 4.1) + `hub/index.html` (standalone)
  3. `productModel.$ref` rewritten hub-relative (`../04-…yaml`) so hub/ links
     the root manifest instead of duplicating it — single source of truth kept
  4. committed catalog re-validated with THEIR SDK (`validate --json` →
     `valid:true, errors:[]`) + `odpc-summary` self-check
- `tools/build-hub.sh` — the wrapper (idempotent, 4-step chain above; every
  step asserts, e.g. exactly-1 `$ref` before rewrite; `valid is True and
  errors == []` after)
- Supporting artifacts: `hub/README.md` (what/why, SSOT rule, regen, deploy
  path); `00-README.md` index rows for `benchmarks/metrics/` (had slipped out),
  `hub/`, `rust/` + refreshed the stale "nothing is built yet" status line

## Deviations from card

- Staging: card's scratch-dir step became a `mktemp -d` inside the script
  (repeatability of the final artifact was the DoD, so scratch exploration was
  folded into the committed pipeline).
- Card's "`resources` + explain output as needed" → used `refs` (their SDK's
  reference listing — proves the ODPC→ODPS link structure) + `explain` +
  `odpc-summary` as the humans-checkable output; `resources` (SDK's own bundled
  resource listing) wasn't needed.
- `$ref` post-processing added: SDK emits the staged filename verbatim
  (`04-…yaml`); committed under hub/ it must be hub-relative. Thin, targeted,
  asserted-only-when-count==1 transform — accordance kept by revalidating AFTER
  the rewrite (step 4 runs on the committed file).

## Discoveries

1. **odpc-build is already production-shaped:** validates inputs (schema-gated;
   `--no-validate` exists but unused), emits the explain line with
   productReferences counts, generates standalone HTML — the "static
   generation" half of the claim needs zero extra tooling. The Git-repo +
   Actions half remains a deploy-time task (README documents the mapping).
2. **Their ODPC↔ODPS reference model works with relative refs:** `refs`
   reports `source_spec: odpc → target_spec: odps`; nothing required absolute
   URLs, so catalog-in-repo → manifest-in-repo is valid per their machinery —
   exactly the "catalog as code" shape.
3. **Idempotency is free:** no timestamps anywhere in catalog.yaml or
   index.html → byte-identical rebuilds → committed artifacts don't churn CI.
4. **odpc-summary hint surfaces ODPG:** "No graph reference found; use
   Catalog.metadata.graph when relationships are implemented in ODPG" — their
   tooling already anticipates graph sidecars; a candidates-on-the-hub graph is
   a natural v1 extension (parked, not invented).

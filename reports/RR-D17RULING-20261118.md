# RR-D17RULING-20261118 — owner ruling: packages and registries stay unreleased until enough data

Owner decision 2026-11-18, verbatim:

> yes, packages and registries will be kept unreleased until we have enough data

That rules D17 as **(c) hold**, with a stated condition rather than a date: **enough data**. The owner did not
define a threshold, sample size, metric, or date; this card does not invent one. "Enough data" is the owner's
judgment at a later point, not a gate the review lane can declare met on its own.

## Scope, from the corrected D17 record (`RR-D17SCOPE-20261118`)

- **Unreleased:** npm, crates.io, PyPI, the OpenCode npm submission, and the Hermes catalog entry (which waits on
  a release SHA). All four `@ctxvm/*` npm packages are currently E404 and `private: true` — this ruling keeps that
  state deliberate rather than accidental.
- **Not affected:** the public GitHub repository, the committed white-paper PDF, the ODPS hub, and the XERJ
  listing. Those are already public and remain so.
- **Consent rule preserved:** whenever a release eventually happens, D6/D14 still binds — no registry release ships
  capture as silent default-on; a first-run notice naming the trace directory and the opt-out is the minimum.
  G4 (redaction §4-LIST go/defer) and the release rule remain open for that future release.
- **No package/version bump, tag, registry action, catalog submission, or push** is authorized by this ruling. The
  owner pushes.

## Why this is a ruling and not a project-state claim

I did not evaluate whether "enough data" exists today. The review lane's earlier cards already name open
measurement gaps — e.g. the paging gate's n=4 under the new fault semantics and the small W8C cell count — but
deciding that those are sufficient is the owner's call. If the owner later says the threshold is met, record that
as a new ruling with the data it rests on.

# RR-H12SHADOW-20261118 — why the stable mode never engaged: a stale profile-local plugin copy won the bare-name import

The diagnostic run's plan block said `policyMode: None`, `modeExplicit: False` — so the policy dict the **engine**
read did not contain the key at all, while the file next to the engine did. This card is the root cause, the fix,
and the class of bug it belongs to.

## 1. The measurement that ended the guessing

`h12-diag` (one paged prompt, free, 27.8 s) — the three fields added for exactly this:

```
reason: fits | budgetTokens 24000 | selectionMode: fresh
policyMode: None | policyModeSource: None | modeExplicit: False
```

`modeExplicit: False` rules out a caller pinning the mode; `policyMode: None` says the dict had no key; the
adoption therefore had nothing to adopt. But `policy(w8cn-paged)` called directly returns
`selectionMode: stable / settings`, and an in-process host emulation adopts it with `trigger: held`. Working
outside the gateway and not inside it is the signature of a **module identity** problem, not a logic one.

## 2. The cause

```
~/.hermes/profiles/w8cn-{naive,paged}/plugins/ctxvm-tracer  -> symlink to the shared install (0.13.27)
~/.hermes/profiles/w8cp-{naive,paged}/plugins/ctxvm-tracer  -> REAL DIRECTORIES, PLUGIN_VERSION 0.13.23 (12 Nov)
```

The gateway is **one process serving every profile**, and the plugin loader puts each profile's plugin directory
on `sys.path`. The engine's sibling import was a bare name:

```python
from profile_policy import policy as _policy_for_turn
```

A bare name resolves through `sys.modules`/`sys.path`. The `w8cp` pair — the paid arm, untouched since W8C — still
carried **0.13.23** copies whose `profile_policy.py` has no `selectionMode` branch. That module won the import, so
the engine read a policy dict from the old scanner while its own directory held the new one adding
`selectionMode: stable`.

This is the hazard the lane's own notes describe for **state** ("a bare `from context_engine import …` resolves by
bare name through `sys.modules`, so a module-level counter can be one object shared by every profile"). It has now
been measured for **code**: a stale profile-local copy can shadow the sibling a plugin actually ships with.

Why the earlier checks missed it: every negative check ran in a *fresh process* with the right `sys.path`, and
each returned `stable`. The gateway's `sys.path` is the one with four profile plugin directories in it.

## 3. The fix, in three layers

1. **Load the sibling by path.** `context_engine._policy_module()` imports
   `Path(__file__).parent / "profile_policy.py"` under its own module name. Identity becomes a property of the
   directory the engine lives in, not of whatever a profile put on `sys.path`. This is the durable fix — it holds
   even if a fifth profile appears with another stale copy.
2. **Remove the shadow.** The two `w8cp` real directories are replaced with symlinks to the shared install (the
   originals kept as `ctxvm-tracer.old-0.13.23` beside them). All four experiment profiles now point at one build.
3. **Pin the arm in the suite.** With the by-path loader the resolver now *succeeds* inside the tests and returns
   the operator's real home (control), which silently inerts every law; the test module pins the arm through
   `ce._POLICY_MOD`, as the developer prompt requires, and the two arm-policy tests stub that loader instead of the
   `sys.modules` module a bare import used to bind.

## 6. The lesson, in one line

**A plugin that imports its siblings by bare name is reading whatever the host's `sys.path` happens to hold — and
a host that serves several profiles can put another profile's stale copy there.** Load siblings by path.

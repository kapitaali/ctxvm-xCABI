# RR-C3FIX-20261111 — C3 made TRUE of our own tree: `ident.ts` sorts by Unicode code point (the
## default sort's UTF-16 order was a silent digest divergence), with a Python-generated cross-language
## vector file, the C3 wording amended to reject-not-coerce, and no digest moved anywhere

Card: the review of the landed note found the load-bearing defect — **C3 was false for ctxvm itself**:
`packages/node/src/ident.ts:20` used `Object.keys(obj).sort()`, which compares UTF-16 code units, while
Python's `sort_keys=True` compares code points. For U+FF00 vs U+1D11E, JS put the astral key first
(its first unit 0xD834) and Python last. The owner chose option (a) — fix the comparator — and the
review added wording, range and trap requirements. This card records the fix, the enforcement, the
verification that **no existing digest moved**, and the items that remain routed.

## 1. The fix

**`packages/node/src/ident.ts`** — a new `compareCodePoints(a, b)` used by `canonicalJson`: it compares
**Unicode code points** (via `Array.from`, the string iterator's whole-code-point yield), with a
prefix-first tie-break. That is the order Python's `sort_keys=True` uses, and the order C3 requires;
Rust's `serde_json` `BTreeMap` agrees with it by construction (UTF-8 byte order == code-point order),
so the odd one out was TypeScript.

**`packages/node/test/tracer.test.ts`** — two new tests: (i) `canonicalJson` sorts by code point (the
astral/BMP pair, a nested case, a shared-prefix case, and the unchanged ASCII case, with the expected
bytes taken from Python); (ii) the **canonical-form vector file** test, below.

**`rust/crates/ctxvm-conformance/vectors/canonical-form-cases.jsonl`** — 12 cases, each with the input
JSON **text**, the expected canonical bytes and the expected digest (`sha256:<8 hex>`), all generated
by **Python's `canonical_json`** (the reference implementation), written ASCII-safe so the lone-surrogate
case is representable: `ascii`, `astral-key`, `nested-astral`, `prefix-key`, `max-safe-int`,
`control-chars`, `nfc`, `nfd`, plus the reject cases `beyond-2^53`, `integral-float`, `negative-zero`,
`lone-surrogate`. The NFC and NFD cases have **different digests** (`sha256:0ca09f1d` vs
`sha256:eed5dc86`) — the no-normalisation rule, pinned. The file is meant to be run by umpire's Python
side too (their lane), so C3 becomes a tested property on both sides rather than a description.

**`validateHashInput(value, path)`** (new, exported from `ident.ts`) — the consumer half of C3:
non-integer numbers, integers outside ±(2^53−1), `-0`, and lone surrogates in strings are rejected
with the path in the message. **It is exported and tested but NOT wired into the minting path** — that
is deliberate and named below.

## 2. The C3 wording amendments (the review's points 4 and 2)

- **Reject, not coerce**, with the duty **split** because the two implementations can only see part
  of it: the **producer MUST NOT put a float in a hash input** (the spelling is unrecoverable —
  `JSON.parse("1.0")` yields the number `1`, so a consumer cannot tell an integral float from an
  integer, while Python keeps the float and would spell it `1.0`); and a consumer that meets a float
  value MUST reject it, never coerce it.
- **Integer range**: integers must satisfy `|n| ≤ 2^53 − 1`; a larger one is not exactly
  representable in an IEEE-754 double, so a consumer MUST reject it or the producer MUST carry it as a
  **string**.
- **`-0` is not admissible** (indistinguishable from `0` in a double).
- **Strings must be valid Unicode scalar values**: a lone surrogate MUST be rejected, not escaped (JS's
  `JSON.stringify` escapes lone surrogates; Python with `ensure_ascii=False` emits them raw and the
  UTF-8 encoding then fails).
- **No normalisation is applied**: NFC and NFD forms are different inputs and hash differently; the
  producer owns normalisation.
- **C3 now points at its committed enforcement** (the vector file + the TS test that runs it).

## 3. Verified: no digest moved anywhere

- **Independent scan before the change**: 44 hashed input files (umpire's calibration corpora v2/v3, its
  fixtures and harness captures; ctxvm's `corpus/m*` and the conformance vectors) — **0 keys outside
  the BMP and 0 astral characters in values**. Since only object KEYS are sorted, the fix cannot move
  any existing digest. (This is the precise form of the "no fixture churn" claim: it holds for *any*
  input whose keys are all in the BMP, whatever its values contain.)
- **After the change, the full CI is ALL GATES GREEN**: `check-node-build: OK — 16 events byte-identical`
  (the node build's golden bytes unmoved), corpus checksums verified, `SCHEMA CONFORMANCE: PASS (682
  checks)`, export round-trip OK, hub byte-identity green, TS suites **24** (my two new tests) and the
  python suites unchanged.
- **The edge case the owner asked to be named**: a tool call whose arguments contain an astral-plane
  **key** would get a **different `logicalRef`** after this change (its canonical bytes change) — a
  negligible edge case, named here as the owner required.
- **The wiring that is deliberately NOT done**: calling `validateHashInput` from the minting path would
  make a tool call whose arguments carry an integral float fail to mint a ref — a behavioural change
  with a blast radius beyond the note (traces would fail rather than hash differently). That is
  owner-routed and named as the follow-up; the note's rule stands as written, and C3 is now enforced
  where it can be (the canonical-form vector).

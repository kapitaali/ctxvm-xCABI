## Deviations from card

1. **The sealed validator was not edited.** The proposal §7 item 2 said "teach
   `spec/rfc-0/validate_schema.py` the `schemaVersion` branch". D4's ruling is
   "sealed v0 stays byte-identical", and the owner's sealed-surface rule governs, so
   the branch lives in the new `spec/rfc-0.1/validate_schema_v0_1.py` instead. The
   boundary is still proven mechanically from the new file (it loads both schemas and
   asserts rejection in both directions).
2. **R1 emission is not in this card.** Proposal §5.1 (emitters learn R1) is deferred;
   see Discoveries 2 for why the deferral now blocks W2b.
3. **The RFC text is a new file**, `spec/rfc-0.1/RFC-0.1-xCABI.md`, not an edit to
   RFC-0 (`02-xcabi-events-v0.md`).
4. **Message text changed for one rejected input.** A v0 trace carrying an RFC-0.1
   field previously failed inside serde (`unknown variant`); it now fails with a named
   R0 contract. Exit code is unchanged (2). `RR-W7-20261029` quotes the old text — that
   quote remains true of the pre-card binary and is left unedited (append-only).

## Discoveries

1. **The R0 gate was dead code when first written.** `check_version()` existed in the
   codec but nothing called it: `replay` exited **0** on `design/rfc-0.1/ab-demo.after.jsonl`,
   silently accepting a v0 trace with `intentional_rerun` — exactly the "consumer must
   reject, never guess" case R0 forbids. Found by verification, fixed by wiring all four
   CLI read sites, pinned by `replay_core_rejects_rfc01_fields_on_a_v0_trace`, which
   goes red if the wire is removed. The bookkeeping note matters more than the bug: a
   version contract that only exists in a library nobody calls is not a contract.
2. **No adapter emits `schemaVersion`.** `grep -rn schemaVersion packages/` = 0 matches
   across node, opencode, hermes, ai-sdk. Since `providerUsage` and `ts` are v0.1-only
   and the sealed v0 validator rejects them, **W2b (provider-reported usage) cannot
   emit anything until an emitter card lands.** That card is now the critical path for
   W2b, W1's `providerReported: 0/32` finding, and every downstream cost claim.
3. **The v0.1 vector must be serializer-canonical, not proposal-canonical.** The
   proposal fixture orders `schemaVersion` first and `turn` before `page`; the Rust
   writer emits tag order after `tokenizerId` and `page` before `turn`. The roundtrip
   test caught the difference — a hand-ordered vector would have shipped non-canonical
   bytes. Future vectors: generate from the writer, never by hand.
4. **`check_version` is stricter than the schema on one axis.** It rejects
   `providerUsage`, `ts`, `turn`, `latencyMs` and `intentional_rerun` on any trace
   without `schemaVersion`, including a v0 trace that some other consumer might accept
   structurally. This is deliberate (R0 is a consumer law, not a schema law), but it
   means the CLI gate is the real boundary — the schema alone would let a marker-less
   file through. Both are now tested.
5. **`cachedInputTokens` is optional, and absent ≠ null.** The schema admits `null`
   only for `headroom` (matching v0's existing `optionalInt`); every other optional
   field is omit-when-unknown. Emitters must not write `null` placeholders.

## Open questions

1. One emitter card or two? `schemaVersion` + `providerUsage` + `ts` + `turn` could ship
   as a single "v0.1 emission" card across the four lanes, or split so the version
   switch lands first (cheap, unblocks everything) and the fields follow. Recommendation:
   split — the version switch is one line per adapter and immediately makes W2b emittable.
2. Does `ts` emission need to be opt-in per lane? It changes the bytes of every future
   drop, so each drop's checksums and provenance shift. If any capture needs stable
   bytes, the switch has to be per-trace, not per-version.
3. Does v0.1 emission require a `manifest.yaml` `productVersion` bump and a hub regen,
   or can both versions coexist under one product version? Decide before the first
   v0.1 drop, not after.

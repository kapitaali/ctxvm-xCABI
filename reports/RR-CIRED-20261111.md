## 2. Reproduced: two failures, one file, one line of cause

A clean checkout of the pushed SHA (`0ba4f8f4`, detached worktree) with the rust binaries available
(`CTXVM_RUST_BIN_DIR` → the build) gives **2 failed, 187 passed**:

```
FAILED test/test_generate_traces.py::GenerateTests::test_live_shape_session_exercises_the_scan
        live-shape generator regression: identifier_scan silent on string history (B1-class death)
FAILED test/test_generate_traces.py::GenerateTests::test_all_history_messages_are_plain_strings
        (it calls the same generator, which raises)
```

**Cause:** the committed `packages/hermes/test/generate_traces.py` still asserts the **pre-0.12.0**
behaviour — the live-shape trace must carry an `identifier_scan` fault. Plugin 0.12.0 aligned the
observer (prose mentions are telemetry; `identifier_scan` emits no fault), so `make_live_shape_trace()`
now trips that guard and the suite is red. **The fix is one file** — `packages/hermes/test/generate_traces.py`
— and the other lane has **already written it** in their working tree (the guard becomes: the scan's
mention count ≥ 1, and the only remaining fault source is `tool_recall`). It simply was not committed.

**A reproduction artefact worth recording, because it misleads:** the first clean-checkout run showed
**six** failures — the two above plus three UC1-handoff and one UC2-golden-parity failure with the
message *"golden drift at corpus/m2/live-thrash.jsonl turn 0"* (`{'fault': 'inconclusive', 'reason':
'no page.fault at …'} != {'fault': 'model-reasoning', …}`). Those four are **not** real failures: the
UC1/UC2 forensics shell out to the rust binaries (`uc2_forensics.py::_run` → `ctxvm profile`), and a
fresh checkout has no `rust/target/`, so the profiler cannot run and the golden comparison degrades to
"no page.fault at turn 0". Point `CTXVM_RUST_BIN_DIR` at a build and they pass ✓. Anyone reproducing
this from a clean checkout should know that, or they will chase four phantom failures.

## 3. Why the local gate was green — and the hole in the repo's own tooling

Two local gates said green, and both were telling the truth about **the working tree**, not about the
**pushed commit**:

- `tools/run-ci.sh` runs the **working tree**, where the other lane's uncommitted guard rewrite is
  present → 196 passed ✓.
- `tools/ci-rehearsal.py` — whose docstring says it "clones the committed tree … exactly what
  actions/checkout gives you" — actually **overlays the dirty tree** (tracked edits + untracked files)
  and commits that overlay inside the clone: *"Rehearse what would be PUSHED, not just what is
  committed."* The implementation comment was right and the **docstring was wrong**; and because the
  overlay carries the uncommitted fix, the rehearsal was green too.

So the repo had **no local gate that could see the hosted failure** — the exact class the rehearsal was
built for ("catches green-only-because-of-uncommitted-state", `AGENTS.md` §2).

## 4. The tooling fix in this lane: `ci-rehearsal.py --committed`

`tools/ci-rehearsal.py` now takes **`--committed`**, which **skips the working-tree overlay**: the clone
then holds exactly the committed tree — what `actions/checkout` gives the runner — and the docstring
says so plainly, including *why* the default can be green while the hosted run is red.

**Witness (the reproduction, one command):**

```
$ python3 tools/ci-rehearsal.py --committed --job ts
  ✔ [14] install pytest (hermes + benchmarks/metrics suites)
  ✖ [15] @ctxvm/hermes tests (full suite: plugin + uc_registry + uc2_forensics)  → exit 1
  FAILED test/test_generate_traces.py::GenerateTests::test_all_history_messages_are_plain_strings
  FAILED test/test_generate_traces.py::GenerateTests::test_live_shape_session_exercises_the_scan
  2 failed, 194 passed, 1 warning, 15 subtests passed in 1.38s
FAIL ts: @ctxvm/hermes tests (full suite: plugin + uc_registry + uc2_forensics)
rehearsal FAILED (1/1 jobs)
```

That is the hosted failure, reproduced locally, from the committed tree alone ✓ — and the same command
will be **green** the moment the missing file is committed.

## 5. What is needed to turn the hosted gate green (and who owns it)

**One file, one commit: `packages/hermes/test/generate_traces.py`** — the other lane's path, already
rewritten in their working tree. This lane does **not** stage another lane's path (the shared-index
law), so the fix is either theirs to commit, or the owner can say the word and this lane will commit
their working-tree bytes verbatim.

**The standing lesson, now in the tools:** *a green local gate is evidence about the working tree; the
gate that decides the pushed commit is `ci-rehearsal.py --committed`.* Before a push that must not turn
the hosted gate red, run that.

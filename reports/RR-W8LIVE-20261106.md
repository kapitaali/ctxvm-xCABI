## Finding 1 — a real provider receipt rides the wire

From the 12-event partial written at 13:07:15 by plugin 0.10.0:

```
call.meta keys : type, turn, provider, cacheEstimate, providerUsage, ts
providerUsage  : {inputTokens: 663, outputTokens: 358, cachedInputTokens: 326,528}
cacheEstimate  : {estHitTokens: 0, estMissTokens: 0, providerReported: false}
session.open   : model deepseek/deepseek-v4.1-flash-1017, provider unknown,
                 environmentId env-2b4652ae9d98, schemaVersion "0.1"
```

This is the host's own `post_api_request` summary, through the strict intake: 326,528 cached reads with
663 uncached input is the prompt-minus-cache derivation computed on real numbers, not a fixture.

**The divergence is the point.** The page-table estimate reads zero hits and zero misses while the
provider reports 326,528 cached reads. The v0 estimate counts pages only and does not tokenize the
non-page prompt, so for a long session it is not merely optimistic or pessimistic — it is a different
quantity. That is why the receipt is a separate fact rather than an in-place upgrade of `cacheEstimate`,
and it is a caution for the W8 analysis: the est columns are page-table-only, and the receipt columns are
the only cache truth in the record.

## Finding 2 — the engine registers, and stays inert

The witness shows `engine=ctxvm registered` at 13:05:58. The host source decides whether that matters
(`agent/agent_init.py:1816`): `context.engine` defaults to `"compressor"`, and that value returns
`None` before any plugin lookup, so a registered engine is not auto-activated. The owner's config has no
`context.engine` key, so this machine is still on the built-in compressor — the paged arm stays opt-in,
as the design requires, and everyday work is not being paged.

## Finding 3 — the last W17 square is still open

No `read_file` or `search_files` call appears in any witness row since the restart (or any earlier one):
1,183 rows at the last count, zero reads. Every declare therefore still carries the fail-safe `MUTATING`,
which is correct and does not exercise the registered-`READ_ONLY` path. One file read closes it.

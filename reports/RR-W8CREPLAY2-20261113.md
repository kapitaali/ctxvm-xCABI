## 2. Why it is turn-invariant, and what that means for the claim

The plugin's own comment states the rule ✓ (`packages/hermes/src/plugin.py:229` ✓):
*"the wire: the trace's `residentTokens` is pinned to ctxvm-core's whole-table…"* ✓ and
`packages/hermes/live/__init__.py:863` ✓ says the same for the live adapter ✓.

⇒ **The `turn.render.residentTokens` field is the whole table's residency, not the turn's** ✓✓ — and the
trace's own values confirm it ✓: `residentTokens = 86,569` on **every** turn 0→19 ✓ (the 21 pages'
declared tokens summed ✓ = 86,569 ✓), while the *request* size (`prefix.approxInputTokens`) rises
10,772 → 67,024 ✓ and then plateaus ✓.

⇒ Therefore **"0 stubbed" is not a per-turn observation** ✓✓ — it is the same fact at every turn ✓,
because **the trace contains no `page.evict` row at all** ✓ (0 of 81 events ✓) and therefore the
derived table has no slot that could ever be stubbed ✓✓.

### What the 0-stub result does witness ✓
- It is consistent with the policy's **removal** semantics ✓ (no stub is introduced, so no slot is
  stubbed ✓) and it is derived by `ctxvm-core` from the trace alone ✓✓.
- It confirms the **sealed-v0 semantics**: a stub is a `page.evict` with `stubText` ✓, and this policy
  emits none ✓ ⇒ the engine cannot be "stubbing behind the trace's back" ✓✓ — if it had substituted
  stubs in the request, the request would carry *smaller* page bodies while the table still showed them
  full ✓, and the request-size plateau (~63–67 k) is consistent with **removal** ✓ (a stub-substituting
  policy would have held the request at the budget with stubText in place ✓✓ — the request does not
  shrink to the budget ✓✓).

### What the 0-stub result cannot witness ✓
- It **cannot** witness *per-turn* eviction behaviour ✓✓ — the projection is turn-invariant here ✓
  precisely because the table never changes ✓.
- It **cannot** be compared against the corpus's stubbed-eviction surface ✓: `corpus/m1` has 4
  `page.evict` events ✓ (the README's own limitation row ✓: *"All 4 `page.evict` events in `corpus/` sit
  on one synthetic trace (m1/session-thrashing); the 10 real captures have zero"* ✓), so the corpus
  contains **no real stubbed eviction to compare against** ✓✓ — and the live captures contain **no
  `page.evict` row at all** ✓.

⇒ **The honest statement**: the trace's absence of `page.evict` is *itself* the evidence that this
policy removes pages rather than substituting stubs ✓✓ — the 0-stub table is the *same* fact seen from
the core's side ✓, and the two agree ✓✓. What does **not** exist is a **contrast case** (a real capture
with stubbed evictions) against which to *measure* the difference ✓✓.

## 3. The two-number mechanism sentence, once more, with the table's invariance in view

```
table holds                86,569 tokens   (constant, every turn ✓)
the 9 pages removed        38,764 tokens   (part-02 … part-10 ✓, sidecar `evictedPages` ✓)
declared minus removed     47,805 tokens   (page content still in the table ✓)
request at turn 12         63,379 tokens   (= 47,805 page content + ~15,574 scaffold ✓)
```

⇒ The gap between *"the table holds 86,569"* and *"the request carries ~63,379"* is **not** only
eviction ✓ — it is **eviction (38,764) + scaffold (~15,574)** ✓✓. The mechanism sentence is right in
substance ✓ and the two numbers are each right ✓, but they are **not like-for-like** ✓ (table residency
vs request size ✓) — the same point as `reports/RR-W8CREPLAY-20261112.md` §3 ✓, now with the invariance
established ✓.

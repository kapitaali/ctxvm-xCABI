The three clauses, with their provenance:

- **C1 — A page's identity is verb-dependent.** `page.declare` nests it (`page.id.logicalRef`,
  `page.id.contentHash`); every other page-carrying verb carries it flat (`page.render`, `page.evict`,
  `page.fault`, `page.pin`, `page.unpin`). A consumer MUST dispatch on the **event type**, never on
  which fields happen to be present. *Provenance: the P10 answer's rule, verbatim in substance ("Read a
  page's identity from `page.id.logicalRef` and `page.id.contentHash` when the event type is
  `page.declare`, and from `page.logicalRef` and `page.contentHash` for every other page-carrying
  verb; dispatch on event type, never on which fields happen to be present"), plus its reason — "a
  reader that accepts either shape by sniffing fields will silently pass a malformed line" — which
  this lane then MEASURED: the validator rejects a `page.declare` carrying a flat identity, and
  `tools/waste-report.mjs:79` is exactly such a sniffing reader in this repo.*
- **C2 — Key order within an event is not significant to parsing or replay** … "the codec remains
  strict about unknown fields" … "see the conformance test". *Provenance: the P11 answer's proposed
  line, with the test locator added: the landed vector pair
  `vectors/order-{struct,sorted}-{ts,nots}.jsonl`, the expected report `order-expected-report.json`,
  and `tests/key_order.rs`.* One inference is made explicit in the file: the page table is a **pure
  function of the parsed model** (`ctxvm_core::render::derive_projection`: "Pure function of decisions
  fed"), so equal parsed models entail equal derived page tables — which is what lets C2 speak of
  replay without the test asserting that level directly (see §4).
- **C3 — The canonical form of a hash input (normative, for hash inputs only):** keys sorted by
  **Unicode code point**, minimal separators, no ASCII escaping, and a restricted value set —
  strings, exact integers, booleans, null, arrays, objects; **floats not admissible** (the repo's
  standing convention bans floats from identity comparisons, `RR-W7-20261029.md` §4; a float-bearing
  hash input is therefore outside the clause). *Provenance: the P11 answer's own conditional — "if
  one [a digest or chain] is computed over serialised bytes, key order matters for it, and the note
  must say so" — triggered by this lane's measurement that umpire's ref truncation digest
  (`decide_ref` → `hex8(canonical)`) is exactly such a digest, and that the two implementations'
  canonical forms differ today on astral-plane KEY names (Python sorts by code point, the TS
  `canonicalJson` uses the default UTF-16 code-unit sort) and on number spelling (`1.0`/"1",
  `1e+16`/"10000000000000000", `1e-07`/"1e-7", big integers past 2^53).* The file states that these
  differences produce different digests **silently**.

## 3. What the note deliberately does NOT do

- It adds **no field** (P10's ruling) → the five-touchpoint law is untouched, and no codec, schema or
  validator byte changed.
- It says **nothing normative about a trace line's key order** (law 3 forbids it) — C2 is about what a
  consumer must ACCEPT, never about what an emitter must EMIT; the byte forms differ by construction
  (`ts` last vs before `type`).
- It does not touch the sealed `spec/rfc-0/`, nor the existing `RFC-0.1-xCABI.md` text.
- It does not claim the cache question is settled (P9's H3 stays unknown-cause), and it makes no
  cost claim of any kind (law 7).

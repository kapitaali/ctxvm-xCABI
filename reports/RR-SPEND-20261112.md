## 3. The review side's reading of cell-02's limits (the owner's five points, endorsed)

1. **The accuracy PASS is near-guaranteed by the task** ✓ — a sequential census needs only counts per
   part, and the model's own text keeps those counts, so parity says nothing about tasks that revisit
   old content, and the **faults** (the heart of paging) cannot occur. **Consequence for the next cell's
   task (the review side's addition): the task must REVIST old content** — otherwise pins and faults
   cannot occur and the cell measures nothing about the mechanism ✓ — and the artefact must then be
   able to *detect a wrong answer*, i.e. it must require the **content**, not only the counts ✓.
2. **"210,856 tokens evicted" is easy to misread** ✓ — the honest figure is the net reduction (final
   request 64,733 against 107,794, **0.60×** ✓). The claim set must lead with the net reduction and keep
   the per-turn re-drop sum as what the trace's counter says, named ✓.
3. **The mechanism now has a plausible explanation** — eviction ran about 7 of 20 turns (~15 calls), and
   the ~682k excess of uncached tokens is ~45k per engaged call, which fits a dropped-set change each
   turn invalidating most of the prefix ✓. **Labelled as the owner's inference from the numbers, not a
   measurement** ✓ — and it is **falsifiable**: a drop-once-hold (watermark) policy removes the per-turn
   prefix invalidation, so the excess should fall by roughly the number of engaged turns ✓ — a cheap
   prediction for the next card, and the first thing a zero-spend simulation could check ✓.
4. **Booking despite the mismatch**: the reason is sound (a specification error, not an instrument
   failure) ✓, but it was decided after seeing the result ✓ — so **the refined rule must be ratified
   before the next block** ✓ (the proposal is in §4 below ✓).
5. **One pair on a free model**: the scoping is right ✓ — "first counted cell" must not become a general
   claim ✓ (the claim set in `reports/RR-W8CCELL02RUN-20261112.md` §5 ✓).

## 4. The refined prediction-block rule — PROPOSED, for the owner's ratification before the next block

The rule lives in `reports/W8-SPEND.md` §Prediction (the W8 lane's file ✓ — this lane proposes, the owner
ratifies ✓):

```
1  every predicted quantity names its UNIT (tokens / USD / a ratio between which two, and whether the
   quantity is a net reduction or a per-turn sum);
2  the onset is predicted as "the first turn the unconstrained request exceeds the budget, plus the
   engine's lag" - never as a turn number;
3  a MISMATCH whose cause is identified as a specification error - recorded, explained and corrected -
   is a RECORDED DEVIATION, not a void;
4  a mismatch with an UNEXPLAINED cause remains INSTRUMENT-BUG: stop, do not book the cell.
```

(3) is the new part, and it exists because the rule's purpose is to catch a **broken instrument** — a
mismatch whose cause is known and is *our* specification is not an instrument fault ✓. The cost of (3) is
that the judgement happens after the result, so (3) must be **ratified before the block is written**, not
after ✓ — which is exactly why it is in front of the owner now ✓.

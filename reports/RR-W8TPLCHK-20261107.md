## Template 1 — flags.json: computable, with two traps and a good property

Mechanism (proven): each of the six `rust/crates/ctxvm-conformance/src/bin/*.rs` parses its own
arguments in a hand-rolled `match` block (no shared flag/parsing module imports flags into the bins; the
shared `cli.rs` names no flag literal). The parse-arm truth is mechanically derivable and was stable across
runs. Scrubbed accepted-flag vectors (dropping error-literal noise: bare `--`, and the `--turn:` /
`--event:` / `--source:` prefixes quoted inside error strings):

```
diff.rs      --help --output -h
export.rs    --force --help --odps --output --turn -h
profile.rs   --event --help --output --source --turns -h
replay.rs    --help --output --pin --turn -h
stream.rs    --help --json -h
tokens.rs    --file --help --tokenizer -h
```

**Trap 1 — the USAGE doc lies about its own binary.** `tokens.rs`'s doc block names `--features tiktoken`
(a *cargo* build flag), and the doc's flag set (`--features`, `--file`) is not the parser's (`--tokenizer`,
`--file`). A checker derived from usage text would encode the wrong truth on this bin. The frozen checker
must come from the parse arms, and the task text must say "flags the binary parser accepts" — otherwise the
task is unfreezeable, because two honest readers derive different answers from doc vs parser.

**Trap 2 — string-literal noise.** Naive flag-shaped extraction over the bins also captures error-message
fragments (`--`, `--turn:`, `--event:`, `--source:`, and a comma-embedded `--file,`). Both the task text and
the checker must state the scrub rules, or honest runs disagree with the frozen vector.

**Good property worth keeping:** pressure survives grep here *only because* the checker is exact. A single
`rg`/grep over the bins recovers candidate flags including the doc-only `--features`, so a grep-based answer
fails the exact parse-arm vector on `tokens.rs`. The exact checker is what defeats the one-shot collapse —
keep the exactness in every checker, not just the JSON shape.

**Pressure arithmetic (hole).** The whole template-1 fixture is 32,443 chars ≈ **7,089 tokens ≈ 5 pages** at
the ~1.5k cap. Two bins exceed the cap if read whole (`profile.rs` ≈ 1,713 tok; `export.rs` ≈ 1,565 tok) —
both must be read in chunks smaller than the page cap, which is fine, but the task's maximum *declared*
input is the whole fixture: ~7k tokens. The design's bar (§2.1 of the plan: 40–60 pages, 45–70k declared)
is unreachable by an order of magnitude. Either this template's expected declared volume joins the freeze
list at its real value (~7k), or more work must be required per bin — the plan today promises the bar
without per-template arithmetic.

## Template 2 — drops.json: computable once "sessions" is a choice; fixture is small

Mechanism (proven): per drop, `sha256sum -c checksums.sha256` (all eight PASS on this tree) gives the
checksum status; `*.meta.json` sidecars give `sessionID`s; the `.jsonl` rows give pages, declares, and
faults by source. Measured ground truth (×2 stable):

```
m1: rows 105  chars 13,959  pages 25  faults {identifier_scan:5, tool_recall:4}  sidecar sessions 0
m2: rows  55  chars  7,563  pages 16  faults {identifier_scan:7, tool_recall:6}  sidecar sessions 2
m3: rows  46  chars  6,863  pages 16  faults {identifier_scan:2, tool_recall:6}  sidecar sessions 2
m4: rows  23  chars  4,976  pages 18  faults {tool_recall:1}                     sidecar sessions 1
m5: rows  80  chars 16,304  pages 34  faults {identifier_scan:17}                sidecar sessions 1
m6: rows  45  chars  6,319  pages 14  faults {identifier_scan:7}                 sidecar sessions 2
m7: rows  69  chars 14,684  pages 51  faults {}                                  sidecar sessions 2
m8: rows  53  chars  6,817  pages 12  faults {identifier_scan:3, tool_recall:4}  sidecar sessions 2
totals: 476 rows, 77,485 chars (~19,371 tok), 186 distinct pages
```

Definitions the T0 freeze must pin (each changes the expected JSON):

- **sessions.** No `.jsonl` row anywhere in the eight drops carries a session key, so "sessions" cannot be
  derived from rows (v0-era `session.open` carries none — m1 predates sidecars entirely). The only
  mechanical sources are the sidecar `sessionID`s (m2–m8; m1 has two honest fallbacks: its four `.jsonl`
  file count or the digit 0). Note `ctxvm stream` groups by `environmentId`, which these frozen pre-W14
  drops do not carry — the tracer CLI cannot answer this question; pin the sidecar definition.
- **distinct pages.** Pin it as the number of distinct `page` values across `page.*` rows of the drop
  (m7's 51 is a once-per-turn format; m4's 18 include many repeats — the definition matters).
- **m7's zero faults** is a real expected value (pause/resume drop contributes nothing to fault
  classification) — do not treat an empty map as an error in the checker.
- **handoff/* scope** — no drop has one today; pin "flat files only" or "rglob" before it matters.

**Pressure arithmetic (hole).** Every corpus byte is 77,485 chars ≈ **19,371 tokens ≈ 13 pages**. Reading
*everything* does not reach 40–60 pages or 45–70k declared; the digest itself is a handful of integers.
Each drop's digest is derivable by one short `jq`/`awk` command, and the plan's own pressure line ("one
command output per drop" per drop) contradicts the bar it imports from the design. This template needs its
declared-volume expectation split (digest answer ≈ 8–16 calls, fixture ceiling ≈ 19k elsewhere) or a
heavier artefact.

## Template 3 — deltas.json: the prototype proves the spec page and the core enum agree — which is itself the hole

The plan's template 3 hands the model a spec page stating five behaviours and asks it to find violating
modules in `packages/*/src` (the plan says 20 files). I prototyped checker predicates against the repo's
own open spec source (`02-xcabi-events-v0.md`, 3,658 chars ≈ 915 tok) and the core's wire vocabulary:

- **P1 verb vocabulary** — event-type-shaped literals in `packages/*/src`: all nine v0 verbs verified; the
  four "unknown" shapes are extraction noise, not types (`session.ts` is a file name, `trace.jsonl` a path,
  `session.context`, `trace.stats` doc/prose). A naive checker over type-shaped strings fires on prose —
  the frozen definition must be "literals emitted as event types".
- **P2 derived-events stay out** — no `trace.gc` anywhere in packages sources. Empty violator set today.
- **P3 spec-table vs core enum** — mechanically scraped both sides (the spec page's Events table; the
  `#[serde(rename = …)]` values inside `pub enum Event` in `rust/crates/ctxvm-codec/src/model.rs`): the
  sets are **exactly equal** to the nine verbs (spec-only = ∅, core-only = ∅). Computationally stable and
  unique — and an empty-violation set.
- **P4 fault-source vocabulary** — no `tool_recall|identifier_scan|explicit_api` literals anywhere in
  packages sources (fault emission lives outside `packages/*/src`). A packages-only scan asserts nothing
  about real compliance: false negative by construction.
- **P5 append-only (runtime invariant)** — static scans see only three write-mode hits, all in
  `packages/node/src/flush.ts` (lines 176/197/201). Whether that violates "append-only" cannot be decided
  from source text alone — it is a runtime/event-sequence property. Answer: the checker for such a
  behaviour must be event-level (replay the trace and assert ordering), not grep-level.

**The hole, proved:** if the authored T0 behaviours resemble these — behaviours the tree genuinely
satisfies — the expected `deltas.json` is five empty sets and the exact-equality checker is satisfiable
by writing five empty arrays before reading anything. That is the plan-hole class "checker satisfiable
without the work", and it passes silently. Two mitigations, both to freeze at T0: (a) author each
behaviour such that its violator list is non-empty, with the owner computing the expected list by the same
mechanical rule; (b) require the artefact to carry per-file evidence rows (each of the 20 files names a
finding or "no violation, checked because …") so the checker verifies *substance*, not absence.

**One number from the plan is confirmed by a different rule than the plan implies.** `packages/*/src`
-with-dist-and-node_modules-excluded = exactly **20** files. But "all `.ts`+`.py` under `packages/`" =
53, and "all `.ts` under `packages/`" = 33. The frozen task text must enumerate the 20 paths (or pin the
glob rules); a checker derived from a different glob counts a different population and the template
silently changes size.

**Pressure arithmetic.** The full `packages/*/src` read is 57,049 chars ≈ **57,049//4 ≈ 57k tokens ≈ 39
pages**, plus the spec page (915 tok) and, if the checker needs it, `model.rs` (≈3,986 tok — over the cap;
chunk it). Template 3 is the *only* ctxvm template whose full sweep lands near the 40–60-page band —
but only if reading is per-file and not collapsed into one grep. If the authored answer is a small
violator set, one `rg` recovers it and no per-file reading is ever needed: the same one-shot-collapse
risk as template 2, stronger because the answer is short.

## Template 4 — release.md: computable, and the pressure bar is unreachable as scripted (with a DQ trap)

Mechanism (proven): the last twelve `reports/LOG.md` rows are uniquely identifiable, dates ascending, and
derivable by one command — `tail -12 reports/LOG.md | awk -F'|'`:

- full twelve rows: 18,035 chars ≈ **4,509 tokens** (≈3 pages at the cap);
- ids + dates + track only: **436 chars** — the expected minimal artefact is *less than one page*.

"Exact ordered IDs + dates" as the checker therefore passes on a basically-free answer. Worse, the row
summaries are quiz-sized (the twelve rows average ~1,500 chars each) and LOG ordering is already ascending,
so even the "ordering forces retention" pressure claim is weak: one tail command observes the stored order
directly. If the template wants real pressure it must pull from the *cited indexes* (each of the twelve
rows names an RR report; the twelve RR files are the real read mass at ~0.5–1.5k tok each — an order of
magnitude more than the rows themselves). As scripted, the declared expectation must be revised downward
or the artefact made heavier at T0.

**The DQ trap, reproduced against the real gate (Hole 5):** I ran the actual
`tools/dq-secret-scan.py` over synthetic stand-ins for the model-likely surfaces. Results:

| Surface | Scan verdict | Firing pattern |
|---|---|---|
| last-12 LOG rows quoted verbatim | **CANNOT-SHIP (exit 1)** | `path.abs_home` |
| ids + dates + track only | SHIP-UNBLOCKED (exit 0) | — |
| bin usage/doc fragments (incl. `--features`) | SHIP-UNBLOCKED (exit 0) | — |
| template-2 digest with sidecar `sessionID`s + page refs | SHIP-UNBLOCKED (exit 0) | — |
| a row quoting `/home/theb/…` absolute path | **CANNOT-SHIP (exit 1)** | `path.abs_home` |
| synthetic `sk-`-shaped filler | **CANNOT-SHIP (exit 1)** | `openai.sk` |

The scan's law held: **no matched bytes ever printed to stdout** — verdicts name patterns, positions and
SHAs only. The trap: the "W8-impl" row in the last twelve quotes the DQ scan's own pattern list
("emails, `/home/` paths, IPv4"), and `path.abs_home` matches that phrasing — so a model quoting even the
*index row it is asked to summarize verbatim* burns the run's drop bytes (the drop is never retried).
The escape is structural: either the frozen expected `release.md` avoids verbatim row quoting for that one
row, or the release task's required content is limited to ids + dates + track + a *paraphrase* of each row
(summary raggedness stays DQ-safe). This changes what template 4's artefact may demand, so it belongs in
the T0 freeze list, not post-hoc.

## Cross-template findings (one card's worth, so the owner can freeze with eyes open)

1. **Per-template pressure is one-sided in the plan.** The design's 45–70k declared / 40–60 pages bar
   cannot be reached by templates 1 (fixture ≈ 7k tok), 2 (≈ 19k tok), or 4 (rows-only ≈ 4.5k tok) even
   if every byte is read. Template 3 (≈ 57k tok sweep) and templates 5–6 (unknown, second repo) are the
   only ones near the bar. Either the freeze list records the per-template declared expectation, or the
   artefacts must be made heavier (e.g., template 4 must cite the RR files; template 2 must demand
   per-drop per-file detail). Today the plan promises the band with per-template numbers unreconciled —
   that is a design drift waiting at the pilot, not a fatal flaw.
2. **Frozen-tool-set ↔ checker-strictness is the real lever.** One-shot collapse commands exist for every
   template (per-drop `jq` for 2; whole-src `rg` for 3; `tail | awk` for 4; a loop+`grep` for 1 — though
   grep fails the exact tokens.rs row). The per-task frozen tool set must name these as absent (no
   compound/looping shell, no scripting interpreters, no whole-tree search classes) — the checker being
   *exact* is what turns a grep answer into a wrong answer, so exactness belongs on the freeze list next
   to the tool set, not just as a "mechanical checker" property.
3. **The terminal is in/out.** For templates where the checker needs the *model's own knowledge of what
   the tool would return* (parse-arm flags vs doc text), the task texts must say what the artefact should
   record — the flags, or the command used? — otherwise a DQ-safe run can still record content the
   checker cannot judge.
4. **DQ trap mitigation is a freeze-time step, not a fallback.** Add to the plan's §8 acceptance list,
   before run #1: *every frozen expected artefact (templates 1–4) itself passes `tools/dq-secret-scan.py`
   exit 0*. Today acceptance 2 only gates the pilot's drop set from the run, which happens after the runs
   — the trap can cost the drop-set bytes before anyone notices.

# RR-LESSONS2-20261109 — the pair that counted, and what it cost to get there

Card: documentation. No code, no spend. Companion to `RR-LESSONS-20261109`; this one records what the
first counted pair taught, which is mainly about the cache and about why four instrument iterations
were spent on a property this deployment cannot have.

## 1. The result, in the currency that matters

```
            calls   input        cache-read   cache-write   peak     cost
naive          5    336,358        227,410      108,933    59,793   $0.0175
paged         14  1,057,053         83,042      973,969    65,488   $0.1264
NTR -2.14        paged 3.14x input, 7.2x dollars
```

Selection on every call moves the request prefix; the provider's prefix cache then misses. Cache
reads fall to a third, cache writes rise ninefold. The token ratio is bad and the dollar ratio is
worse, which is the tell: **tokens were never the right currency once a cached input class exists.**
Both artefacts are parsed-equal and correct, so this is not an accuracy effect.

## 2. Why four witnesses failed, stated once

| attempt | what it read | why it was wrong |
|---|---|---|
| `engine` at load | `build_engine()` ran | construction, not use — "ctxvm" on a naive arm |
| module counter | `ACTIVATIONS` | flat sibling import resolves by bare name: shared across profiles |
| instance counter | `self._selections` | the host deep-copies the engine per agent; the clone counted |
| shared meter | `self._meter` | correct fix for the clone, still one module for every profile |

The last row is the one to remember. A plugin installed in `~/.hermes/plugins/` is loaded once for the
gateway: the loader gives the first scope the bare module name and later scopes a `__home_<digest>`
suffix, so shared-directory plugins have **one** namespace, one `state`, one engine object, one
counter for every profile. Both arms of the pair read `engineSelections: 14` for that reason.

The rule I should have applied before writing any of it: **read the install path, not the loader
logic.** A per-arm witness is a deployment property. Where the plugin sits decides whether any
in-process field can ever distinguish an arm.

## 3. What replaced the witness

Runner-side attribution: the `-p` in the ledger row, with the two profiles differing in exactly one
key. `engineSelections > 0` corroborates that *a* ctxvm engine ran in the process; it is never a
differential. The plan (§4e) now says this instead of proposing a fifth attempt.

## 4. The surface, and how cheaply it was settled

The control arm's `execute_code` looked structural and was not: toolset `file` resolves to
`patch, read_file, search_files, write_file`, and the run had simply omitted `-t`. One flag, $0.0221,
and the model read the fixture on its own — 32 reads, 8 calls. Tier 1 (read-only MCP server) was
cancelled. **Print the resolved tool list before building a replacement surface.**

## 5. The gate ruling that saved a second null

The Tier 0 cell produced every value correctly and failed byte-exactness by writing per-file objects
inline. Byte-exactness is a JSON-style requirement, and two arms failing on style is a null about
indentation. The gate is now **parsed equality**, with formatting recorded per cell as an observation.

## 6. What the negative result implies for the next question

Not "paging is useless". The engine's strategy is incompatible with prefix caching, and that is an
engine property:

- a selection that changes only when the resident set actually changes keeps the cache;
- an unconditional re-selection per call cannot, at any `vBudget`.

The next test is therefore one cell after one engine change — stable prefix across calls where the
resident set is unchanged — reporting prefix identity per call, not forty-eight cells of the current
shape. At this shape a grid would spend about $6 to re-measure −2.14.

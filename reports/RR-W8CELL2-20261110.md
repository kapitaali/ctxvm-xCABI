## 1. The floor is 53,790, not 49,419 — and the budget sat 1,210 above it

From the capture's own numbers: system prompt 21,932 B ≈ 5,483 tokens, first three turns 13,240,
last six turns (6–11) 35,067.

```
floor  ≈ 53,790      budget 55,000      remain ≈ 1,210
```

`_plan` also subtracts scaffold tokens (assistant messages that are neither hard-kept nor pages),
which the 29-request session accumulated. With scaffold the protected mass passes 55,000 and the
engine returns early by L5 — the same mechanism as the 24,000 run, one decimal place higher. The
request peak was **79,960**, so pressure exists; the budget is simply under the floor plus scaffold.

Next budget: **72,000** — above floor + scaffold, below the 79,960 peak.

## 2. The artefact is wrong in the same way as H6, and the task text is the cause

```
total_long  599   correct        (independently recomputed)
widest_file part-09.txt           truth: part-12.txt (51 long lines vs 45)
```

Two independent runs, two different surfaces, the same mistake. The model is reading "widest" as
*the longest line*, not *the most lines over 100 bytes*. That is a comprehension failure produced by a
task label, not an arm effect — but a gate both arms fail measures wording, not context policy.
The task text now says explicitly: the file with the largest `long` count, **not** the longest line,
tie-break by filename ascending.

## 3. `turn.render.residentTokens` is flat — the instrument defect is confirmed at 12 turns

All twelve renders carry `residentTokens: 61134`, `evictedTokens: 0`, `headroom: null`. `finish()`
computes the resident total once at flush and stamps it into every render (RR-W8INST). The real series
is `perApiRequest`: **29 requests, peak 79,960, median 41,624**.

Consequence for the protocol: evictions and residency must never be read from `turn.render`. The
verifier still uses `evictedTokens` from those rows, which is correct (it is a sum of what the engine
reported per turn), but any per-turn curve must come from `perApiRequest`.

## 2. The two divergences measured today (why the proposed second assertion is unsatisfiable as stated)

The reviewer's second assertion is "Python and TS produce identical canonical bytes, and therefore
identical `page_id`, for the same input — include non-ASCII text, nested keys, and a number case".
Measured today, on the two implementations the repo actually has (umpire's Python `canonical_json` vs
ctxvm's TS `canonicalJson`, the declared mirror pair):

```
ascii      IDENTICAL    {"a":{"y":[1,2],"z":1},"b":"x","k":"v"}
nonascii   IDENTICAL    {"a":{"y":["é"],"z":1},"b":"café über","k":"à"}
nested     IDENTICAL    {"a":{"a":3,"b":{"c":2,"d":1}},"z":1}
astral     *** DIFFER ***
  py:   {"a":3,"�":1,"😀":2}
  node: {"a":3,"😀":2,"�":1}
```

**Divergence 1 — astral-plane KEY names.** Python's `sort_keys=True` orders by Unicode code point;
JS's default `Array.sort` orders by UTF-16 code units, so a key in plane 1 sorts before U+FFFD in
JS and after it in Python. Different byte order ⇒ different canonical bytes ⇒ **different digest**,
silently. Note the value side is fine (non-ASCII values are identical) — the trap is in KEY names
only, which is why `ensure_ascii=False` alone does not make the two implementations equivalent.

**Divergence 2 — number text forms.** Python `json.dumps` vs JS `JSON.stringify`:

```
1.0                 -> "1.0"        vs "1"
1e16                -> "1e+16"      vs "10000000000000000"
1e-7                -> "1e-07"      vs "1e-7"
1e30                -> "1e+30"      vs "1e+30"        (agree)
0.1+0.2             -> "0.30000000000000004" vs "0.30000000000000004"  (agree)
12345678901234567890-> "12345678901234567890" vs "12345678901234567000"  (JS loses precision past 2^53)
```

Four of six differ, and the bytes differ **without any error**. This is the reviewer's "number case",
and it is decisive: the W7 card already recorded the scope caveat "floats banned" — the byte
comparison was never run over the cases where the two languages disagree. So "the canonical form of a
hash input must match byte for byte across languages" is **not satisfiable as stated**: it can only be
made true by SPECIFYING the canonical form — ordering by Unicode code point (and changing the TS
side's `Array.sort` to match), plus a number encoding rule (or a restriction to integers), plus the
string-escaping rule (`ensure_ascii=False` ≡ `JSON.stringify`). A note that merely says "byte-for-byte
across languages" leaves a false claim in normative text.

**(b) The reviewer's "sniffing" hazard is real, and its scope is this repo — in the waste-metrics

```js

```

A **presence-based fallback**: it takes the nested `page.id.logicalRef` if present, else the flat

reviewer's note forbids: "a reader that accepts either shape by sniffing fields will silently pass a

flat identity ("1 failure(s)"), yet `waste-report.mjs` would accept and key that line silently — so the
tool and the validator disagree, and the tool is the one that feeds the waste metrics (the "lens"
feeding W3's metrics). A malformed `page.render` carrying a nested `page.id` would likewise be read as
"no page" rather than rejected.

**Consequences for the note (and for its priority):** clause C1 is not hypothetical — it names a
reader that exists in this repo, and it says dispatch on the EVENT TYPE. A follow-up worth the owner's

# RR-W8CACHE-20261110 — C1: where do the cache writes come from?

Zero spend. Sources: the captures named in the card, their `call.meta` and `turn.render` rows, and
`experiments/usage-day-summary-a93f8b06-2026-11-10.csv`. The rule was written before the numbers were
read, as the card requires.

## Decision rule (pre-registered)

- **H1 (engine rewrite)** is supported if, on requests with zero evictions, the request is NOT
  append-only — i.e. the message count or request size falls, the system prompt changes, or the
  serialised message order changes between consecutive calls.
- **H2 (idle gap)** is supported if writes follow gaps longer than the provider's cache lifetime.
  Lifetime is **UNVERIFIED**: it is not recorded in the capture, and I will not assert one from
  memory.
- **H3** if neither pattern fits.
- A hypothesis is **not testable** if the field it needs is missing or corrupt; that is recorded as
  UNKNOWN, not as support.

## 1. The per-request series does not exist in the trace, and one field is corrupt

```
call.meta rows in w8-cell-01:            12   (one per TURN, not per request)
API requests in the sidecar:             29
providerUsage.inputTokens, every row:     3
providerUsage.cachedInputTokens:      15,621 -> 51,582   (this is the REQUEST SIZE)
```

`inputTokens: 3` on all twelve rows is not a value; it is the field mis-mapped. What the plugin records
as `cachedInputTokens` tracks the prompt size exactly (15.6k → 51.6k), and there is **no cache-write
field at all** in the wire. So per-request cache attribution is **UNKNOWN** from the capture, and every
number below comes from the provider export, which is per day per key, not per call.

## 2. What the capture does answer: the request is append-only

`w8-cell-01`, the twelve `turn.render` rows, which carry the measured prefix:

```
turn  systemPromptBytes  messageCount  requestChars  approxInputTokens
  0        21,932              7           43,084          10,771
  3        21,932             30          104,832          26,208
  6        21,932             54          166,496          41,624
  9        21,932             78          225,452          56,363
 11        21,932            128          299,004          74,751
```

Monotonic in every column; the system prompt is **byte-constant**. No turn loses a message, no turn
shrinks, no turn re-orders. That is the shape of append-only growth, and it is what H1 predicted would
NOT be seen.

**H1 verdict: NOT SUPPORTED.** The engine's early return is not rewriting history — C2 proves the same
thing at the unit level, by bytes.

## 3. The write volume is real, and larger than the growth

```
provider, 2026-11-10, openai/gpt-6-luna:  input 115,377,888
                                          cache_read 113,109,046
                                          cache_write 33,459,752   over 819 requests
                                          = 40.9k written per request (day average)
w8-cell-01:                               1,353,671 write over 29 calls = 46.7k per call
its request growth per call:              ~5k-9k tokens
```

So the write volume is 5–9× the new content. Something is writing the prefix again, and it is not the
engine's message list, which grows monotonically.

Two candidates remain, and the capture cannot separate them:

- **provider accounting** — the export may count a cache *checkpoint* as a write of the whole prefix
  even when it was also read. The day totals are consistent with that: 113.1 M read and 33.5 M written
  over 115.4 M input means most requests both hit and wrote.
- **session-boundary effects** — twelve separate `hermes chat` invocations open twelve prompts; each
  prompt's first request may be a cold prefix even though the text is identical, if the cache key
  includes something not in the text.

**H2 verdict: NOT TESTABLE.** Gaps between calls in `w8-cell-01` are ~18 s (09:43:34 → 09:47:07 for 29
requests), far below any plausible lifetime, and the lifetime itself is not recorded — UNVERIFIED.

**H3 is therefore where this lands: UNKNOWN cause, with H1 excluded and H2 untestable.**

## 4. What the reviewer's first finding now says

The reviewer inferred "the engine rewrites the prefix" from writes-per-call ≈ request size. The
inference was reasonable and the data does not support it: the request is append-only, the system
prompt is constant, and the engine returns byte-identical content when it does not evict (C2). The cost
is real; the cause is not the engine's message list.

## 5. What would settle it (proposals, not edits)

```
1  record per-request cache_read / cache_write / prefixHash in the coverage sidecar
   (the wire has no cache-write field; the sidecar already carries perApiRequest)
2  one probe against the same prefix twice, back to back, and diff the export's
   cache_write for that key: it separates provider accounting from session boundaries
3  fix providerUsage.inputTokens — a field that reads 3 on a 50k request is worse than absent
```

## 6. Data missing, stated

- per-request cache read/write: absent
- cache lifetime: not recorded
- scaffold token mass per request: not recorded (this also blocks C3)
- the day export covers one UTC day only (C5)

# RR-OCDSH-20261116 — exposing the OpenCode model catalog inside DeepSeek Harness

**Lane:** opencode. **Date:** 2026-11-16. **Scope:** connection/transport integration only; no
repo source changed, no DSH fork source changed, no paid call made. **Outcome:** the OpenCode
models are now installed as a DSH connection and a DSH profile, and the route authenticates and
lists all 50 models; a live generation is **not verified** because the free endpoint returns
`429 FreeUsageLimitError` for every stored credential. This is a no-go on live verification, not
a claim that the route works end to end.

## 1. The question and the answer

**Question.** How do we get the models OpenCode can use (`opencode/*`) to show up in DeepSeek
Harness (DSH, at `~/Apps/deepseek-harness`) so the W22 plugin can be developed against them?

**Answer.** DSH already has the `dsh connection` feature (the fork's `connection-profiles`
branch). OpenCode's `opencode` provider is an **OpenAI-compatible** endpoint,
`https://opencode.ai/inference/openai/v1`. So no adapter or plugin change is needed: add a DSH
connection with `--route pi-ai`, point it at that endpoint, store a working OpenCode credential
under the resulting `OPENCODE_API_KEY` ref, refresh the model catalog from the endpoint, and apply
the connection to a profile. The models then appear in DSH's model list and the profile's default
model can be pinned to a free one.

## 2. What was verified, in order

### 2.1 The endpoint and the credential

OpenCode's own CLI does not print the provider's baseURL, but the installed binary binds the
`opencode` provider to an OpenAI-compatible route. This was confirmed externally by a `GET
/models` against that URL with each stored credential (both returned **HTTP 200, 50 models**).
No key value appears in this card.

The stale credential is identified first so it is not reused: `~/.dsh/.credentials.yaml` already
held `OPENCODE_ZEN_API_KEY` (imported from Hermes by `pnpm run setup:hermes`). With a browser
User-Agent to pass Cloudflare, both candidate OpenCode endpoints returned
`401 {"code":"api_key_expired"}` for that key. It is **not** the key to use.

The working credentials are in OpenCode's own auth store. `opencode auth export` showed two active
entries:

| integrationID | type | expiry |
|---|---|---|
| `opencode` | oauth (access + refresh) | 2026-11-23 |
| `opencode-go` | key | none |

Both authenticated successfully against `https://opencode.ai/inference/openai/v1/models`. The
`opencode-go` key was chosen for DSH because it has no expiry. The export was written to a scratch
file, used once, and the exact files were removed immediately; no secret was printed or committed.

### 2.2 The model list

`GET https://opencode.ai/inference/openai/v1/models` with either valid credential returns **50**
model ids, unprefixed (e.g. `deepseek-v4.1-flash-free`, `longcat-2.5-free`). OpenCode's own catalog
(`opencode models`, `tools.opencode.models` with `all: true`) reports the same 50 under the
`opencode/` prefix: **12** carry catalog cost 0, **38** carry nonzero catalog rates. This is a
catalog fact, not a spend or saving claim.

The DSH endpoint list is what gets stored in the connection, so the IDs in the DSH profile are
bare (`deepseek-v4.1-flash-free`), not `opencode/deepseek-v4.1-flash-free`.

### 2.3 The DSH connection, applied

From `~/Apps/deepseek-harness` (where `pnpm` is invoked as `npx --no-install pnpm` in this shell;
the CLI itself runs via `node --import tsx/esm apps/cli/src/bin.ts`):

```sh
# $KEY is read from the stored OpenCode credential; never echoed, never committed.
node --import tsx/esm apps/cli/src/bin.ts connection add opencode \
  --url https://opencode.ai/inference/openai/v1 \
  --route pi-ai --api openai-completions \
  --model deepseek-v4.1-flash-free --context-window 1048576 \
  --key "$KEY"
# dsh: saved connection "opencode" (https://opencode.ai/inference/openai/v1) as OPENCODE_API_KEY

npx --no-install pnpm run refresh:connections opencode
#   opencode: 50 models from https://opencode.ai/inference/openai/v1 (added default reasoning efforts)

node --import tsx/esm apps/cli/src/bin.ts connection use opencode opencode \
  --from-default-profile headless
# dsh: profile "opencode" now uses connection "opencode" (https://opencode.ai/inference/openai/v1)
```

`dsh connection show opencode` reports `route pi-ai`, `apiKeyEnv OPENCODE_API_KEY`,
`model deepseek-v4.1-flash-free`, `api openai-completions`, `context 1048576`. Pinning `--model`
is deliberate: `applyPiAiConnection` uses `connection.model` for the `agent-default-model` row,
so the profile starts on a cost-0 model even though the catalog also contains paid ones. The
written profile at `~/.dsh/profiles/opencode/cordis.patch.yml` carries the `llm-pi-ai` provider
`opencode` with 50 models and the default-model row:

```yaml
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: opencode
    model: deepseek-v4.1-flash-free
```

### 2.4 The live call — blocked, and why that is still evidence

The headless bundle disables the interactive credential store, so the credential ref was exported
into the launch environment (value read from the DSH credential store, never printed):

The profile already boots `@deepseek-ai/dsh-headless` (its `package.json` bundles `dsh-base` and
`dsh-headless`), so the launch form is **`pnpm dsh opencode "<task>"`** — there is no separate
`headless` app selector. An earlier attempt in this card used
`dsh --profile opencode headless "Reply with exactly: OK"`; that appended the literal word
`headless` to the task text (the headless runner joins all positional args into `Config.task`).
The corrected run below is the one whose result is claimed:

```sh
OPENCODE_API_KEY="$KEY" npx --no-install pnpm dsh opencode "Reply with exactly: OK"
# $ node --import tsx/esm apps/cli/src/bin.ts opencode 'Reply with exactly: OK'
# dsh: QUOTA: 429: {"type":"FreeUsageLimitError",
#   "message":"Free usage limit reached. Free models work in OpenCode (https://opencode.ai);
#              subscribe to OpenCode Go to keep going: https://opencode.ai/go"}
```

To rule out a wiring or credential defect, the same `POST .../chat/completions` with
`deepseek-v4.1-flash-free` was repeated directly with the `opencode` OAuth access token (with and
without the `x-opencode-org-id` header) and with the `opencode-go` key. **All three returned the
same 429 `FreeUsageLimitError`**, not 401/403. So authentication and routing are correct; the
blocker is the free allowance on the endpoint, which is currently exhausted.

## 3. What may and may not be claimed

**May be claimed.** The OpenCode model catalog is now configured in DSH as a `pi-ai` connection;
it lists 50 models; the default model is `deepseek-v4.1-flash-free`; the route authenticates
(HTTP 200 on `/models`) and reaches the inference path (429 from `/chat/completions`). The
connection did not disturb the four pre-existing DSH connections (`openrouter`, `nvidia`,
`deepseek`, `nous`) or their profiles.

**May not be claimed.** No live generation through DSH was observed, so nothing is established
about model output, about the W22 capture adapter seeing a completed turn on this route, or about
token accounting for it. No cost or saving claim of any kind. No paid model was called. No
"deterministic" claim. No claim that the free allowance resets at a known time — that is
UNVERIFIED.

## 5. Unknowns that stayed unknown

1. When the free allowance resets, or whether it is per-account, per-key, or per-client. The error
   text is the only evidence available; no provider dashboard was consulted.
2. Whether the free tier is intentionally restricted to the OpenCode app (the error text says
   "Free models work in OpenCode"), or whether DSH would work once the allowance resets.
3. Whether a paid `opencode/*` model would succeed from DSH. Not tested: no paid call is
   authorised.
4. Whether the W22 adapter captures a complete trace on this route; that needs one successful
   generation first.
5. The expiry/refresh behaviour of the `opencode-go` key beyond "no expiry field in the auth
   export".

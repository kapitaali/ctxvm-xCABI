## 4. Normalization analysis — the card's "normalize, then diff" step, honestly resolved

The card's v0 normalization targets are **ids and latencies — fields that do not
exist in v0** (RFC-0.1 R3/R4 introduce them). So v0 leaves exactly one thing to
normalize: nothing legitimately non-deterministic — every observed divergence is
structural. The candidate normalization (canonical tool names) was analyzed and
**fails to reach trace equivalence — provable from the four ref/hash pairs**:

- The READ page: refs differ only by tool name (`tool:read` vs `tool:read_file`,
  args identical `{"path":"notes/alpha.md"}`). Under name canonicalization the
  refs WOULD match — and the hashes still diverge (`894152c0` vs `a7e9d484`),
  because the hashed page bodies are harness-native tool receipts (D3).
- The WRITE page: also differs by args shape — opencode's ref carries the file
  body in the args (`"content":"alpha budget = 42\n"` with trailing newline);
  hermes' write args stop at a different shape (D2).

Conclusion: cross-harness `logicalRef`/`contentHash` identity is **not reachable
by field normalization** in v0; cross-harness diff divergence at event 0 is
by-construction behaviour of the identity minting, faithfully reflecting two
harnesses. A canonical-ref/body law is a W7 item (§6), not an adapter edit.

## 6. W7 intake (spec ambiguities fed forward — the RFC-0.1 card absorbs what it can)

1. **Canonical ref law** — `tool:<name>(<canonicalArgs>)` embeds harness-native
   tool names and args shapes; cross-harness diff needs either a declared
   tool-name/args-shape mapping or a normalization VIEW definition. (D1, D2)
2. **Page-body semantics** — Tool.Result pages hash harness-native receipt text;
   receipts dominate token accounting (the logical content here is 17-18 chars as
   `counted` chars; receipts were 10-14 vs 57/37). This is the dominant lever on
   cross-harness token comparability and on any future waste/cost claims. (D3)
3. **Scan coverage on USER-turn emitters** — identifier_scan at pre_llm only
   can never fault pages declared inside the same user turn; either a
   post-LLM/turn-end scan surface (v0.1 candidate) or an explicit coverage law
   (a hermes single-user-turn trace is faults:0 by construction). (D6)
4. **Diff tally semantics** — `tallyMismatches` compares per-turn resident
   counts across harnesses with different turn units AND different token
   regimes; the report should carry a units/regime note or diff gains a
   declared-comparison mode. (D5)
5. **session.open honesty** — hermes plugins cannot always know their model
   (`unknown/unknown` fallback + null sidecar model); RFC-0.1 R2 keeping
   `model_pin`/`seed` OUT of the identity ref is validated by this observation;
   session.open should carry only what the EMITTER knows. (D7)

Plus the R1-evidence pointer for the RFC-0.1 report: the two opencode
`faultOfResidentPage` rows (logged, non-fatal, replay exit 0) are the first live
instances of the exact class proposal R1 promotes to `intentional_rerun`
(resident-valid, exempt from the fault-resident rule, never hard-fault ground
truth).

## W14 — the grouping key the paper's unit needs

TokenEconomizer's unit is a task stream in an environment and its savings appear by roughly the sixth
task; our ledger had per-session identity only, so two sessions in one repository were unrelated rows.

`session.open.environmentId` = `env-` + 12 hex of a SHA-256 over the credential-stripped git remote,
or over the worktree path when there is no origin. Only the digest is emitted — no path, no remote,
no branch (branch changes per task and can name a client). One repository therefore has one id across
clones and machines, and `ts` already gives the ordering, so grouping plus sorting *is* the stream.

**The honest asymmetry:** opencode and ai-sdk derive it from the project directory; the Hermes gateway
does not, because the plugin runs inside the gateway process whose `cwd` is the gateway's, not the
session's. Hashing that would give every session one fake environment — a number that looks like data
and means nothing. That lane emits an id only from an explicit `CTXVM_ENVIRONMENT_ID`, drops a
malformed value instead of coercing it, and a test asserts no absolute path can reach a trace.

**Byte-stability trap avoided:** fixtures pin `env-000000000000` rather than deriving, because a hash
of the CI runner's checkout path differs per machine and would break a byte-identical test for a
reason unrelated to the code.

## W16 — what causality the ledger can actually prove

The essay says: walk back from the failing span along data-dependency edges. The note asks what xCABI
can prove first, and finds a DAG over **pages and turns** at zero bytes — declare→render, residency,
fault→page, turn order — plus two boundaries: `identifier_scan` is an **inferred** touch (labelled as
such, never drawn as an edge), and instance identity is unrecoverable because page refs are
content-derived.

The assumption I expected to write — "the harness must cooperate" — turned out to be false in a good
way: all three lanes already expose a per-call id (hermes `tool_call_id`, opencode `id`/`messageID`,
ai-sdk `toolCallId`). Recommendation: ship the derived view (a `causality` binary) and only record
`callId` if a question needs instance attribution.

## The stream view — what the key was for

W14 shipped `environmentId` and stopped at the field. A grouping key nobody reads is not a
measurement, so this card adds the sixth binary: `ctxvm stream <dir|file>... [--json]` groups trace
files by environment, orders them by start time, and reports per session the declarations, the ones a
render actually showed, the ones no render showed (an upper bound, named as such), faults and resident
tokens — plus a per-environment summary with **declarations repeated across sessions**.

Its first real output, over the live trace directory, is a useful lesson in reading the tool honestly:

```
6 session(s), 131 turn(s), 404 declaration(s), 3 repeated across sessions, 362 fault(s)
environment (unknown)
```

Every session landed in `(unknown)` because the hermes lane cannot derive an environment id — the W14
gap, now visible in the output instead of buried in a design note. Three repeated declarations is
therefore a lower bound on a badly grouped set, not a claim about repetition.

rust 70 → 72; ALL GATES GREEN. README corrected in the same card: six binaries not five, 72 tests not
59, and "For agents" now starts at `AGENTS.md`.

## The plugin learns to explain itself, and a silent no-op surfaces

Asked for: `/ctxvm-help`, `/ctxvm-help <command>`, `/ctxvm-help environment`, and a `/ctxvm-start`
that runs with no arguments. All four landed, plus source labelling on the trace directory
(`slash command` / `env CTXVM_TRACE_DIR` / `start (defaults)`) so an operator can tell where a value
came from.

Two defects came out of the work, both worth the ink:

1. **A no-argument start threw away the configured directory.** `_resolve_trace_dir(None)` returns the
   built-in default without consulting `CTXVM_TRACE_DIR`, so the first version of `/ctxvm-start` sent
   a configured operator to `~/.local/state` regardless. The test now asserts the env path survives.
2. **The version number had never moved.** Both `PLUGIN_VERSION` and `plugin.yaml` were `0.4.1`. The
   W15 and W14 edits searched for `0.4.0`, matched nothing, and reported success — so two reports and
   two commits claimed 0.5.0 and 0.6.0 that did not exist. Corrected in place in both reports, bumped
   to 0.7.0, and a test now asserts the two files agree.

That second one is the same failure class as the gate flake: a mechanism that reports success without
checking. The fix in both cases is an assertion, not a resolution to be careful.

hermes 104 → 108; ALL GATES GREEN; installed copy synced, gateway restart required.

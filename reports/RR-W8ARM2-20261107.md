# RR-W8ARM2-20261107 — the arm witness was broken, and the cell was search-bound

Card: plugin 0.10.5. Two findings from cell A of the slice; one fixed, one that changes the
experiment's shape.

## 1. The witness recorded construction, not activation (fixed)

Cell A was invoked as `-p w8-naive` and its sidecar said:

```
"engine": "ctxvm", "profile": ".hermes"
```

Both fields were wrong, and both for the same reason: they described the process, not the arm.

- `engine` read `state["engine_registered"]`, set when `build_engine()` runs at plugin load —
  and that call is unconditional (recorded in RR-W8FREEZE). Every process therefore reports
  `ctxvm`, including a naive one.
- `profile` read `basename(HERMES_HOME)`. The process that flushes is the multiplexer, whose
  home is `~/.hermes`, so every profile it serves reads `.hermes` regardless of `-p`.

Fixed in 0.10.5: the engine object counts `select_context()` calls (`context_engine.ACTIVATIONS`),
and the manifest records `engine` only when that count is above zero, plus `engineSelections`
as the number itself. `engine: null, engineSelections: 0` is now a real observation: the host
never selected with an engine in that process.

**The limit this exposes, which no field can fix:** activation is a *process* fact. A
multiplexer serving `default`, `w8-naive` and `w8-paged` cannot attest which arm a session
belongs to, because one process runs both engines. The experiment therefore needs **one
gateway per arm** (plan §4c), and the runner must refuse a cell whose gateway serves more than
one profile. `profile` is only meaningful under that rule.

## 2. The cell was search-bound, not page-bound (not fixed — a design finding)

700 declares in cell A, by tool:

```
search_files   686     69,439 tokens
read_file       14     57,489 tokens
distinct refs  632
```

The model searched 686 times. It read fourteen files. The task's anti-collapse premise — that
line shape cannot be produced by a content search — is false in practice: `search_files` with
a pattern like `.{100,}` returns long lines, and a model that believes it can count them will
keep trying. Two fixtures in a row (33 parts, then 13) produced the same behaviour and the same
outcome: `max_iterations_reached(150/150)`, no `flags.json`.

This is the pilot's failure mode, reproduced at a third of the page count, which means page
size was never the binding constraint. The binding constraint is the **tool surface**: with a
content search available, this model does not read files, whatever the task text says.

## What follows

The paging question needs three things at once, and two of them are not in place:

| requirement | state |
|---|---|
| a per-cell arm witness | **fixed** in 0.10.5, but only with one gateway per arm |
| a tool surface where reading is unavoidable | **absent** — 686 searches against 14 reads |
| a task solvable inside the iteration ceiling | **absent** — 150/150 on both fixtures |

Fixing the witness alone changes nothing measurable: the next pair would be two search-bound
runs, one of them with an engine attached, both hitting the ceiling.

## Recommendation

Either build the read/write-only MCP tool surface and raise or remove the iteration ceiling for
both arms as a recorded T0 amendment, or stop. A third patch without those two changes would
spend another $0.33 to rediscover 686 searches.

If the stop is chosen, the negative is already strong and cheap to publish: three cells, $1.15,
and the measurements above — a 4.3x request growth at a 24k budget, 686 of 700 declares from a
content search, the iteration ceiling hit twice, and a tracer whose turn boundary does not fire
for `-z` turns. That is a real result about what a trace-and-page harness can and cannot measure
on this model today.

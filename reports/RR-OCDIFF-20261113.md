# RR-OCDIFF-20261113 — OpenCode vs Hermes: what one turn counts, on the same six-read task

**Lane:** opencode. **Date:** 2026-11-13. **Spend:** $0.00 — both live runs used models the
harness reports as cost 0 (`opencode/deepseek-v4.1-flash-free`, `opencode/longcat-2.5-free`).
**Sample:** n = 1 session per harness per model. **Head:** committed tree at `145e33e` plus this
lane's own card.

**Question.** How does an OpenCode session differ, in measurable counts, from a Hermes session
doing the same work — and does that difference invalidate any comparison the reports already make?

**Short answer.** The harness difference is one definition, not a difference in work: Hermes
records one `turn.render` per user turn and buckets the model requests under it; the OpenCode
adapter records one `turn.render` per model request. On the same six-part read task with the same
free model (longcat-2.5), Hermes produced **6 `turn.render` rows for 12 model requests**, while
OpenCode produced **13 `turn.render` rows for 13 model requests**. The existing Hermes W8/W8C
numbers survive because none of them divides by an OpenCode turn; they stop applying at any
cross-harness per-turn ratio.

---

## 0. Declared rule (written before the comparison in §2–§4)

**Quantity.** Two counts per session: (a) `turn.render` rows, the trace's own turn boundary;
(b) model requests, defined as one completed model call — on Hermes the `perApiRequest` entries in
the coverage sidecar, on OpenCode the `turn.render`/`call.meta` rows (the adapter's turn boundary
is the model request) and the harness's assistant-message count.

**Unit.** One row. The unit must name its harness: *Hermes turn = user turn*; *OpenCode turn =
model request*. These are different units and are never added.

**Against.** The same fixed task — read `part-01.txt` … `part-06.txt` from
`~/Documents/ctxvm/experiments/w8b/ws-naive/fixture`, one read per prompt — on a free model, with
the same model on both sides where a committed Hermes capture permits it.

**What counts as “invalidates the comparison”.**
1. If, for the same task and the same model, the `turn.render` counts differ while the model-request
   counts agree, the difference is **definitional**; any existing claim that uses `turn.render` as a
   cross-harness denominator is **invalid**.
2. If the model-request counts also differ, the excess is **model or tool-surface behaviour**, not
   the harness, and no harness claim may be built on it.
3. A claim whose denominator is a session (dollars, session totals, per-request receipts) or that is
   made **within one harness** is **unaffected** by either case.

**Temporal note, stated so the rule cannot be read as a preregistration.** Path A's first run was
the precondition check and preceded this written rule; the rule governs the comparison and the
longcat control, not the fact that Path A ran. It was not re-specified after the numbers.

The runner polled `GET /api/session/$SID` between prompts until `time.idle` advanced and
`time.busy` cleared, so the six prompts are sequential user turns, not a queued burst. The process
was stopped with `SIGINT` (not `SIGKILL`), which is the adapter's flush owner; the witness records
`cleanup entered → flush → cleanup finishAll → 1 tracer(s) → cleanup exit`.

**Method deviation, disclosed.** Six `opencode run --standalone` invocations would have been six
processes and six flushes; to keep six user prompts inside **one** session and one capture, the
prompts were sent over the local HTTP API of one `opencode serve` process. The plugin, the hook
surface, the adapter, and the flush path are the same ones `opencode run` uses. This is a runner
difference, not a capture difference.

**The load-bearing result.** With the same model and the same six reads, the two harnesses agree on

count, while the Hermes turn count stays at one per user prompt.

## 3. RFC-0.1 field coverage, stated correctly

The question as posed (“does each emission carry `schemaVersion`, `providerUsage`, and `ts` last?”)
needs one correction: **`schemaVersion` is not a per-event field.** RFC-0.1 R0 puts it on
`session.open` only; R3 makes `providerUsage` optional on `call.meta`; R4 makes `ts` optional on
every event and requires the last-key placement when present (`spec/rfc-0.1/RFC-0.1-xCABI.md:8-10`,
`:26-30`, `:32-35`). The table below checks the fields where they belong.

| Capture | `schemaVersion` on `session.open` | `call.meta` with `providerUsage` | `ts` present / last |
|---|---|---|---|
| OpenCode v2.2.7, deepseek free (n=1) | yes (1/1) | **0 / 18** | 73 / 73, last |
| OpenCode v2.2.7, longcat free (n=1) | yes (1/1) | **0 / 13** | 63 / 63, last |
| Hermes 0.13.6, longcat free, 6 prompts (n=1) | yes (1/1) | 6 / 6 | 24 / 24, last |
| Hermes 0.13.15, longcat free, 20 prompts (n=1) | yes (1/1) | 20 / 20 | 82 / 82, last |
| corpus m5 OpenCode (v0) | 0 / 1 | 0 / 14 | 0 / 80 |
| corpus m7-a Hermes (v0) | 0 / 1 | 0 / 5 | 0 / 32 |

The OpenCode absence is **structural in the adapter**, not a property of this run: the live
adapter registers only `session.context`, `tool.execute.before`, and `tool.execute.after`
(`packages/opencode/live/ctxvm.ts:515-580`); `onSessionContext` scans messages and renders, and
there is no usage intake path (`packages/opencode/src/plugin.ts:117-124`). The tracer therefore
cannot emit `providerUsage` on this harness as committed. Whether the v2.2.7 context payload
itself carries a usage field is **UNKNOWN from this tree**; the adapter does not read one.

**One sentence a reader can check.** Every existing Hermes W8/W8C measurement survives, because

cross-harness comparison whose denominator is `turn.render`, where the same six-prompt longcat task
produces **6** rows on Hermes and **13** on OpenCode.

**What this card does not say.** No cost or saving claim of any kind; no token-saving number; no
claim that a model output is deterministic; no safety or evaluation claim from a trace; no claim
that the 2.0/2.17/3.0 requests-per-prompt figures generalise beyond these two models and this
single session each; every count above names its harness.

## 5. Unknowns that stayed unknown

1. **Whether OpenCode v2.2.7's `session.context` payload exposes per-request tokens.** The adapter
   has no intake path, so the trace cannot carry `providerUsage` either way; the host source was not
   read (outside this lane and the tree).
2. **The user-prompt count for corpus m5/m6.** The v0 traces record no user-message event, and the
   READMEs do not state a prompt count. Requests-per-turn for those drops is not derivable.
3. **The exact prompt text of the Hermes six-prompt capture.** The trace records tool calls and
   turn ids, not user messages. The six parts and one read per turn match the task; the wording is
   not in the capture.
4. **Whether the same model served identically on both sides.** Hermes used
   `meituan/longcat-2.5:free` through its provider; OpenCode used `opencode/longcat-2.5-free`
   through the OpenCode provider. The model id matches; weights, quantisation, and serving version
   are not guaranteed identical. This is a same-model-id control, not a same-endpoint control.
5. **Whether a different OpenCode tool surface changes the turn definition.** The adapter's
   one-hook-per-request rule held for 18/18 and 13/13 contexts here; n=1 per model.
6. **Any Hermes request count for the committed v0 corpus.** The `perApiRequest` sidecar is a
   later-plugin field; the v0 drops do not carry it.
7. **Any cross-harness equivalence of page content.** The same file hashes differently; no
   content-level normalisation exists in the tree.

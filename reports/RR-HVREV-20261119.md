## 1. What live verification found

`RR-HARNESSVER` owed a live verification after the operator restarted the gateway (pid 133138,
22:36). That probe **falsified the shipped fix**: the gateway's bundled interpreter
(`~/.hermes/tools/python-3.14.9+…`) raises `importlib.metadata.PackageNotFoundError: No package
metadata was found for hermes-agent`. The host is a **git source install** (`hermes --version` →
`Hermes Agent v0.23.2 … Install method: git`); it carries no importlib distribution metadata. So the
0.13.28 fallback returned **None in the actual runtime** — harnessVersion stayed null live.

**Root cause of the miss:** the original card probed `importlib.metadata.version("hermes-agent")` in
the *authoring shell's* python (which saw a stale pip dist, 0.21.5), not the gateway's interpreter.
The lesson is the lane's own §13: measure the object that does the work, in the runtime that runs it.

## 2. The corrected source

`hermes_cli.version_info.get_version_info()` — the host's **canonical, process-cached** resolver
(install stamp → live git → unknown). Confirmed in the gateway's own interpreter:
`base=0.23.2, display=0.23.2, source=git, commit=ae2a81cc`. `_harness_version()` now resolves,
fail-open at each step (law 5), sidecar-only:

1. `CTXVM_HERMES_VERSION` env override (the parity channel);
2. `hermes_cli.version_info.get_version_info().display_version` (skip `"unknown"`);
3. `importlib.metadata.version("hermes-agent")` — kept as the fallback for environments where
   `hermes_cli` is not importable but the dist is installed (e.g. the offline test env);
4. `None`.

## 3. Conclusive probe (shipped build × actual runtime)

The **installed 0.13.29** module, imported under the **gateway's interpreter** with the source tree
importable (exactly the gateway runtime), returns `_harness_version() == '0.23.2'`; with
`CTXVM_HERMES_VERSION=9.9.9` it returns `'9.9.9'`. The shipped build is correct in the runtime that
will run it — verified before asking for another restart, not after.

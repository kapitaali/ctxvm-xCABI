## 1. What their erratum establishes (from the profile stores, not the driver)

```
w8bn-naive   w8b-20261111-130219-naive   9 API calls   31 messages   21 tool calls   $0.00
w8bn-paged   w8b-20261111-130219-paged   5 API calls   17 messages   11 tool calls   $0.00
w8bn-paged   w8b-20261111-130113-probe   2 API calls    4 messages                  $0.00
```

Both sessions span roughly four minutes (13:02:46 → 13:06:26 and 13:04:49 → 13:09:19) and both end
with **`end_reason = ws_orphan_reap`** — the gateway reaped them because the driver killed the CLI. So
the arms ran, the model answered, and the driver's 120 s cap cut them mid-turn; the capture never
flushed because a killed session is never closed. Their point about the reading: "0 calls" reads as a
provider or transport failure and sends the next agent to the network, whereas the truth is a
task-and-cap failure with a working model.

**The naive arm was a search loop, not progress:** after one `read_file` it made 19 consecutive
`search_files` calls for context it did not need; the prompt allowed `search_files` and said nothing
against it.

**The real blocker is the counting questions.** T-A asks for `long` (lines over 100 bytes) and
`short` (lines under 10 bytes) for every part, but `read_file` reports `total_lines` and `file_size`
only — no character or word counts — so the model must count, and counting a 16.6 kB file invites it to
reproduce the file. Measured today: the counting question on nvidia → 180 s timeout ("[System: Your
previous response was truncated by the output…]" then "This turn did not complete"); on longcat →
300 s timeout (read_file at 17 s, then 283 s of silence) and 120 s timeouts twice earlier during the
arm run; and the **control** — an extractive question, "report the exact text of line 137", same
fixture, same profile, same model, same tool — **completes in 4 s with 2 tool calls**. The difference
is the question, not the model.

**Fixes landed with their erratum:** prompt rules in the digest ("Use read_file only; do not use
`search_files`." for read prompts, "Use read_file and write_file only; …" for the artefact prompt);
SIGTERM first so a timeout terminates the CLI and the session flushes (SIGKILL only after 20 s — the
hard kill is what turned the runs into NO RECORD); a `--limit N` one- or two-prompt smoke check through
the real driver path; `max_turns` 12 → 6 on both `w8bn` profiles so a loop dies inside one prompt; and
`--expect-budget` accepting "any" again (the parser said int, the verifier said any). Verified: with
the rule and `--limit 1`, the naive arm made **1** tool call instead of 21.

**Their recommendation:** rewrite the per-prompt questions to the values the tool reports
(`total_lines`, `file_size`) plus one exact line, and make the artefact those values plus a marker
line — keeping the 20 reads and all the paging pressure, removing counting, and keeping a
parsed-equality gate the checker can recompute. The alternative is a capability-mismatch verdict
(free models cannot count bytes per line), at one more run per model to establish something already
known. Their closing rule is the right one: "No cell was measured, so nothing is invalidated by
changing the task. If the task changes, it changes before a cell exists, not after."

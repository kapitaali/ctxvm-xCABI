# RR-HUBREF-20261111 — the in-flight `hub/catalog.yaml` `$ref` edit will be UNDONE by the hub
## generator (and the gate's own baseline check will restore the old form)

Card: the watcher surfaced an uncommitted edit to `hub/catalog.yaml` alongside the P11 vector work.
This card records the one finding that matters about it, so it is not committed by accident. No hub
byte changed by this lane; no spec/schema/corpus byte changed; no model spend; nothing pushed.

## What the edit does, and what the generator does with it

The edit rewrites the catalogue's single product reference:

```
-      $ref: ../04-odps-dataproduct-corpus.yaml
+      $ref: 04-odps-dataproduct-corpus.yaml
```

But `tools/build-hub.sh` (the hub gate's generator, `tools/run-ci.sh` step "hub regen") **rewrites it
back**, step 3, after the SDK build:

```
old = "$ref: 04-odps-dataproduct-corpus.yaml"
new = "$ref: ../04-odps-dataproduct-corpus.yaml"
n = t.count(old); assert n == 1
```

So the sequence is: the SDK emits the bare form → the script rewrites it to the hub-relative form →
step 5 checks the result against the committed `hub/hub.sha256` baseline, which was hashed from the
**hub-relative** form. Consequences, measured rather than assumed:

1. **The edit cannot survive a gate run.** The next `tools/build-hub.sh` (locally or in CI) overwrites
   `hub/catalog.yaml` and restores `../04-odps-dataproduct-corpus.yaml` — so the committed file and
   the generator's output disagree until the regen runs.
2. **It is not a validation fix.** Tested both forms against the owner's own SDK
   (`venvs/odps/bin/open-data-products validate --json`): the hub-relative form → `valid: true, errors:
   []`; the bare form → `valid: true, errors: []`. **Both validate**, so the edit buys no validity.
3. **If the bare form IS wanted**, two changes are needed together, or the gate will keep undoing it:
   the generator's step-3 rewrite must go (or become a no-op), AND `hub/hub.sha256` must be re-hashed
   over the new form (that baseline is what step 5 checks with `sha256sum -c`).

## Why this lane records it

The hub gate is part of the kit's own CI, and the failure mode is silent: the tree ends up with a
`hub/` diff after every gate run, and the next person to regenerate sees an unexpected change to a
committed artefact. The decision is the hub lane's (or the owner's): revert the edit, or make the
generator and the baseline agree on the bare form. This lane writes no hub byte and stages nothing
here.

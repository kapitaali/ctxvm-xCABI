Run `w8b-20261111-181804`, both arms, 20 prompts, 420 s cap, budget 90,000 on the paged arm only.
Prediction block: `reports/W8B-BLOCK-CELL02-20261111.md`, committed before the run.

Both arms are NO-OP: zero evictions, identical artefacts (paged checker exit 0, canonical bytes).
The paged arm made **43 selections** with `budget 90000 / settings`, all of which returned None.

The run's own table called the paged arm VOID because the verifier was handed 70,000 while the run
used 90,000 — a plumbing bug in the runner, fixed here. Re-verified offline against the same capture
with the right number: nine of ten checks pass, only `evictions > 0` fails, verdict NO-OP.

## The arms are the same arm

```
per-turn request, naive   10,481 → 103,262
per-turn request, paged   11,030 → 102,204
receipt input            181,963 vs 181,632   (0.2%)
receipt cached         2,132,608 vs 2,143,872 (0.5%)
receipt output             2,429 vs 2,243     (8%, both tiny)
```

With zero evictions the engine returns None on every call, so the request is unchanged; the receipts
confirm it. **This is the policy's answer, measured twice:** at 70,000 and at 90,000 the pinned block
plus the protected head and tail already meets or exceeds the budget, so nothing is ever eligible.

The residency peak is 102-104 k. A budget that could bite would have to exceed the floor, which the
two runs bracket at 90-104 k — a window of at most ~14 k tokens on the last two turns of a 20-turn
session, i.e. at most ~7 % of session input, and only after the session is nearly over.

## Two instrument defects found by this run

1. **The verifier was passed the wrong budget** (70,000 hard-coded in the verify call while
   `--budget 90000` drove the run). A sound record was labelled VOID. Fixed: the verify call now takes
   the run's budget.
2. **The session row is not a receipt.** Its `input_tokens` read 225,461 vs 421,914 for two arms whose
   requests were byte-identical; the capture's `call.meta.providerUsage` reads 181,963 vs 181,632. The
   runner now takes tokens from the receipts and keeps the row only for cost and call count.
3. **`engineSelections` was process-global.** The naive sidecar read 2 selections it never made,
   because the meter counted the probes that had run on the treatment in the same gateway. The engine
   now keeps a per-profile bucket (`by_profile`) and the plugin reads the bucket for the session's
   profile. Plugin 0.11.1.

## What may be claimed

Supportable: "at budgets 70,000 and 90,000, over one pair each on `meituan/longcat-2.5:free`, the
fault-pin policy selected 43 times and evicted 0 tokens; the paged arm's requests and receipts were
indistinguishable from the control's within 0.5 %; the artefact was parsed-equal."

Not supportable: any saving, any generalisation to another shape or model, and any claim that paging
is useless in general. The finding is about this policy on a read-once workflow whose harness re-sends
every tool result on every call — where "pin on re-demand" pins nearly everything.

## Recommendation

Close W8B with this negative. Two budgets, one model, an instrument proven to engage, and the same
answer twice: the policy has no purchase on this shape. The alternative — a policy that does not pin
re-sent pages — is a different experiment and needs its own preregistration.

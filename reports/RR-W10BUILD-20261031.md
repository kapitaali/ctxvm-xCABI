## What was done

- **NEW `packages/node/tsconfig.build.json`** — extends the existing typecheck config with
  `noEmit:false`, `declaration`, `outDir:dist`, `rootDir:src`,
  `allowImportingTsExtensions`, `rewriteRelativeImportExtensions`, `include: src/**`.
  `tsconfig.json` is untouched and stays typecheck-only, so in-repo development keeps
  running the `.ts` sources through type stripping with no build step.
- **`packages/node/package.json`** — `exports` now resolves `types`/`import` to `dist/`;
  `files: ["dist", "README.md"]`; `repository` (directory `packages/node`); scripts
  `build` + `prepack`; devDependencies `typescript@^7.0.2` and `@types/node@^22`
  (dev only — the "zero runtime dependencies" claim still holds). `engines` unchanged.
- **`packages/node/src/ident.ts`** — one type-only fix: `canonicalJson` cast the narrowed
  object before indexing (`value[k]` hit TS7053 under the emit config). No behaviour change.
- **`packages/node/LICENSE`** — committed copy of the root Apache-2.0 text, because npm
  cannot include a file above the package directory. `tools/run-ci.sh` gate 2 now runs
  `cmp -s LICENSE packages/node/LICENSE` so the copy cannot drift.
- **NEW `tools/check-node-build.sh`** — the build-parity gate: builds, then replays one
  full trace (3 pages, 3 turns, an identifier scan, 4 model calls) through both the
  type-stripped sources and the emitted `dist/` under the D9 ts opt-out, requiring
  byte-identical JSONL plus agreement on `canonicalJson`/`contentHash`.
- **`.gitignore`** — `dist/` (build output, never committed).
- **Docs** — `packages/node/README.md` gains a "Build (packaging only)" section;
  `design/packaging.md` gains §9 recording the resolution and its disclosed limits.

The parity gate is the load-bearing one. `rewriteRelativeImportExtensions` is what makes
the emit runnable at all — the sources import `./tracer.ts`, so emitted JS must say
`./tracer.js` or plain Node cannot resolve a single import.

## Why the build is packaging-only

The repo ships source on purpose: `README.md` says "no build step is needed in-repo", and
`tsconfig.json` sets `erasableSyntaxOnly` so Node can strip the types. That story is
unchanged — `npm test` still runs `src/*.ts` directly and `dist/` is gitignored. The build
exists because a *registry* consumer is a different runtime: `node_modules/@ctxvm/node/`
may not contain TypeScript. Two artefacts therefore exist, and the parity script is what
keeps "the same package" true.

## Explicitly not done

- **CI does not build it.** `ci.yml`'s ts job installs nothing and runs `node --test` on the
  sources. Wiring `npm ci && npm run build` makes the suite depend on a network install.
  `package-lock.json` is committed so that step is reproducible the day it is approved.
- **No `engines` change.** A compiled tarball would allow a lower floor, but no older Node
  was available to verify it. An unverified floor is not a claim to make.
- **No publish, no tag, no registry metadata submission** (D6/W8 gate).
- No licence re-verification of the new devDependencies beyond their declared licences
  (TypeScript: Apache-2.0; @types/node: MIT) — both compatible with Apache-2.0, and both
  dev-only so they do not enter the published runtime.

## Discoveries

1. **The blocker was smaller than the doc implied but not trivial:** the emit config is
   eight lines; the real work was discovering that `rewriteRelativeImportExtensions` is
   mandatory here (TS-style `.ts` specifiers) and that `erasableSyntaxOnly` had already
   made every source strip-compatible — the same property that makes the emit clean.
2. **`npm pack` silently omits the root LICENSE** (npm ignores paths outside the package
   directory), which is why W10's warning existed. A committed copy plus a `cmp` guard is
   the cheap fix; the alternative was dropping the `license` field's backing file.
3. **`curl` to the npm registry failed while `npm view` succeeded** in this environment —
   the registry is reachable through npm's own transport/proxy but not raw HTTP. Recorded
   because "no network" would have been the wrong conclusion.

## Open questions

- Wire the build into CI (`npm ci && npm run build && node --test`)? It is a posture
  change — the ts job would stop being dependency-free — and the lockfile is ready.
- Does the emitted `dist/` get committed for source-of-truth review, or stay a build
  artifact (current choice)? Committing it doubles the review surface on every src change.
- Should `@ctxvm/opencode` / `@ctxvm/ai-sdk` follow (they are `private: true` today)?

## Addendum (same day) — CI wiring, option 2

The card left "CI does not build it" as a disclosed limit and an open question. The owner
chose **option 2**: install + build + parity in CI, sources still tested as-is. Landed in the
same card.

```yaml
# .github/workflows/ci.yml — ts job
- uses: actions/setup-node@v4
  with:
    node-version: "26"
    cache: npm
    cache-dependency-path: packages/node/package-lock.json
- name: "@ctxvm/node tests (sources, type stripping — no build needed)"
  run: node --test test/
  working-directory: packages/node
- name: "@ctxvm/node install + build (W10: the publishable artifact)"
  run: npm ci --no-audit --no-fund
  working-directory: packages/node
- name: "src-vs-dist parity (a behaviour-changing build fails here)"
  run: bash tools/check-node-build.sh
```

`tools/run-ci.sh` mirrors it step for step (it is documented as the byte-equivalent local
mirror), and `npm ci` costs 0.8 s on a warm cache here, so the mirror runs it unconditionally
rather than behind a "skip if installed" branch — a local gate that behaves differently from
CI is exactly what that mirror exists to prevent.

**Correction to this report's earlier reasoning.** I described a CI install as a posture
change. That was overstated: the ts job **already** runs `pip install pytest`, so it was
never dependency-free or network-free. Adding npm makes it a second package manager in a job
that already had one; it does not introduce a new class of dependency.

**Red-before for the new gate (anti-vacuity).** Setting
`rewriteRelativeImportExtensions: false` in `tsconfig.build.json` makes the build fail with
`TS5096` and `tools/check-node-build.sh` exits 2; restoring the option returns
`OK — 16 events byte-identical`. So a broken build cannot pass the gate.

Honest limit of that witness: it fails at compile time, not at the byte comparison. Inducing
a *silent behaviour* change would mean hand-editing the generated JS, which the script's own
rebuild overwrites; the comparison itself is a plain string equality on full JSONL, so the
failing path is the same `assert.equal`.

**Not claimed:** the Actions run has not been executed — the workflow was validated by
parsing it locally (`yaml.safe_load`, 13 steps in the `ts` job) and every step was exercised
through `tools/run-ci.sh`. The first real Actions run is the owner's push.

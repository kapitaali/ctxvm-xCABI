# RR-W8C-CELL01-20261111 — the policy works and the trace cannot see it

Run `w8b-20261111-202312`, both arms, 20 prompts, budget 60,000, 420 s cap, free tier. Block:
`reports/W8C-BLOCK-CELL01-20261111.md` (committed before the run).

## Verdicts as the runner printed them

```
| w8b-…-naive | 41 | 182,375 | 3,209 | $0.0000 | VOID | 391.5s |
| w8b-…-paged | 41 | 848,636 | 2,329 | $0.0000 | NO-OP | 348.6s |
```

Both labels are wrong, for two different reasons, and the block's own rule turns this into an
**INSTRUMENT-BUG**: predicted evictions 5-20 k at turn 14 or later, verifier saw `evictedTokens 0`.

## The measurement that matters: the request is held at the budget

Per-turn request tokens, from the captures' `turn.render.prefix.approxInputTokens`:

```
naive   10,668 → 15,403 → … → 90,499 → 95,054 → 102,967        keeps growing
paged   10,668 → 15,431 → … → 61,133 → 61,219 → 61,146 → 60,781   flattens at ~61 k
```

```
both cross 60,000 at turn 11
sum over 20 turns   naive 1,108,214   paged 922,911      ratio 0.833
final turn          naive   102,967   paged  60,781      ratio 0.59
```

**The engine is doing exactly what the policy says**: with the text signal removed nothing pins, so
from turn 12 the middle is eligible and the request stops growing at the budget. This is the first run
in the whole card where the treatment visibly acts.

## Why the runner said NO-OP: the trace cannot see the engine

`evictedTokens` is 0 on all 20 turns and there are **no `page.evict` rows** — yet the request is
demonstrably rewritten. The engine returns a new message list to the host; nothing tells the plugin
what it dropped, so the observer records a request that changed without recording why. `page.render`
counts are identical in both arms (19), which is the fingerprint: the evictions happened outside the
trace.

That is instrument defect 1, and it is the last missing link: the engine needs to report its decision
(count and dropped refs) back to the plugin, which then emits `page.evict` and `turn.render.evictedTokens`.

## Why the runner said VOID for the naive arm: a check that does not know the control arm

The verifier requires `engine selections > 0` for every capture. On the control arm zero selections is
the correct answer — the arm exists to select nothing — so a correct control is labelled VOID. The check
must read the capture's `plugin.arm` and invert for `control`.

## The cache consequence, stated plainly

```
receipt input (uncached)   naive 182,375   paged 848,636     4.65x
```

The paged arm's requests are smaller but its **prefix changes every turn**, so the provider cache
misses: the request is rewritten at each selection, and a rewritten prefix is a cache miss by
definition. On the free tier this costs $0.00. On a paid model the same behaviour would cost more
dollars while sending fewer tokens — the exact tension the cache-stability note predicted (TokenPilot,
arXiv:2606.17016v2). It is a design question for the next card, not a bug in this one.

## What may be claimed from this run

Supportable: "at budget 60,000, over one pair on `meituan/longcat-2.5:free`, the paged arm's request
growth stopped at the budget from turn 12 (final request 60,781 against the control's 102,967, 0.59×)
with a parsed-equal artefact, while its uncached provider input was 4.65× the control's."

Not supportable: any eviction count (the trace cannot see it), any cell, any saving, any generalisation.

## The two fixes this run demands

1. **Engine → observer reporting.** The engine reports per-selection `(evicted_tokens, dropped_refs)`
   to the plugin; the plugin emits `page.evict` per dropped page and sets `turn.render.evictedTokens`.
   Until then every future run is blind in exactly this way.
2. **Arm-aware verifier.** `engine selections > 0` becomes `selections == 0` for `arm == control`.
   A correct control must never be labelled VOID.

Neither fix touches the policy, the fixture or the block. Both are instrument work, and both are
prerequisites for the next pair — not re-runs of this one.

## H5 — accepted with three changes

What is good: the design note is specific; the prompt sequence is verbatim and mirrored in `run.py`;
the dry run validates the sequence and writes a manifest (`turns=12, middle=8`); `-c` without a name
is refused; the driver refuses to start without `--arm/--session-name/--workspace/--run-dir`.

**Change 1 — the dependency is not enforced, so the cell would test nothing.** Turn 12 says "use the
early parts you read at the start — do not re-read them unless needed". A model will re-read parts
01–03 at turn 12; that is the cheapest correct path. If it does, evicting the early pages costs
nothing and the cell measures the harness's tolerance for re-reads, not paging.

Fix: make the early material **unavailable** after turn 3 — the driver moves `part-01..03.txt` to a
sealed directory between turns 3 and 4 — and the acceptance checks the capture for any `read_file`
of those parts after turn 3 (must be zero). Without this, H7 cannot produce an accuracy difference
and `evictedTokens > 0` would be the only signal, which is exactly the signal that cannot distinguish
"paging worked" from "the model re-read everything".

**Change 2 — `turns=12` describes the plan, not the host.** Twelve CLI invocations do not necessarily
produce twelve distinct `page.declare.turn` values: the turn counter lives in the plugin's process
state, and if each `hermes -c` starts a fresh process, every invocation is `turn: 0` again and the
capture is single-turn — the exact defect the driver exists to fix. The manifest field must be
`prompts: 12`, and the driver must print the *observed* spread after the run
(`len({declare.turn})`), not before it.

**Change 3 — `-c <name> -z "<prompt>"` is unverified.** Both flags exist (`hermes --help`), but that
the combination continues the same session while remaining one-shot per prompt is an assumption.
H6 must assert the session id is identical across all prompts, and that the capture's session id is
the named one.

## Trace analysis — the numbers I reproduce

```
coverage sidecars present                         65        (report said 71)
distinct declare.turn == 0                        31        (31)
                      == 1                        26        (27)
                       2..6                        4         (8)
                      >= 10                        4         (5)
with budgetSource in the sidecar                   7         (report said none)
with enginePlan                                    0         (0 — correct)
```

**Correction A — "no sidecar carries `budgetSource`" is false.** Seven do, including the diagnostic
cell (`local-6c657975`, plugin 0.10.11, `budgetTokens 24000`, `budgetSource "settings"`). The true
statement is narrower: `enginePlan` is absent everywhere, so the *reason* for a decision is not
recorded — which is exactly what H9 adds, and it does not prevent telling a NO-OP from a selection
when `evictedTokens` is present.

**Correction B — the 25-turn capture is schema-invalid.** `local-a08f0c` is plugin **0.10.2** and
fails `spec/rfc-0.1/validate_schema_v0_1.py` with **37 failures**; all 37 renders carry a negative
`headroom` (e.g. `-225267` against `minimum: 0`), and its `call.meta` rows do not validate under any
branch. Citing it as evidence is fine only with that caveat; counting it in a denominator is not.
Validated captures with ≥10 turns: **three** (`ctxvm-dev-7f` 19 turns, 0.10.5; `local-eea604` 15
turns, 0.10.5; `ctxvm-dev.co` 11 turns, 0.0.1). So "multi-turn sessions are rare" holds, but the
supporting set is 3 of 65, not 5 of 71.

**Correction C — the corpus has no `turn` field at all.** Every `page.declare` in the 17 drops carries
`turn: null`, i.e. the field did not exist when those drops were frozen. "All single-turn" is a
different claim from "the field is absent", and only the second is true.

**Correction D — the task does not fit in 24,000 tokens.** The fixture is **223,634 bytes ≈ 55,909
tokens** (`experiments/w8/t-a/ws-naive-file/fixture`, 14 parts averaging ~16.0 KB), not "14 × 5.6 KB
≈ 19.6 k". The naive arm's measured peak was 59,793. So the premise "even the whole task fits, so
`evictedTokens` may never fire" is inverted: the task is 2.3× the budget, and eviction depends on the
**turn shape** (what the keep law protects), not on the total size. The conclusion ("a negative
result would be publishable") is right; the reason given for it is wrong.

## 2. The acceptance conditions, one by one

| # | condition (`design/w8-cache-stable-selection.md` §4) | result |
|---|---|---|
| 1 | artefact parsed-equal to the naive artefact | **pass** — both PASS, canonical bytes |
| 2 | per-call prefix ≤ 24,000 at some point | **pass** — 22,574 at the last turn, 24,776 peak |
| 3 | `selectionHash` unchanged on the calls between triggers | **fail** — there are no calls between triggers |
| 4 | cache-write below the naive arm's **with cache-read above it** | **fail** — cache-read is 0.22× and uncached input 1.90× |

**Condition 3 fails because the hold never happens.** Across 30 paged calls there are **zero** consecutive pairs
with the same request size — every call in this workload adds a page (the next file) and grows the tail, so
`new-page` or `overflow` fires every time and `stable` degenerates to `fresh`. Stability needs a *repeated*
working set; a read-once sweep has none. That is the design's own precondition, and T-A v2 does not satisfy it.

## 3. The finding that outlives the cell

Even if the hold had engaged, condition 4 could not pass on this shape, and the reason is structural rather than
an implementation gap:

**A provider's prefix cache keys on a prefix. Paging at a 24 k budget must drop from the middle — 69 k of it in
this session — and a hole in the middle truncates prefix reuse at the hole.** Holding the selection is not the
same as keeping the prefix contiguous: holding a hole is still a hole. The design's part 4 (append-only growth)
does not fix it either — it governs how new content is added, not where eviction cuts.

So `selectionMode: stable` is not sufficient for a saving on this workload, and no variant of "hold the choice"
will be. What could work, stated as options rather than claims:

| option | mechanism | cost of finding out |
|---|---|---|
| tail-only eviction | keep a contiguous prefix and cut from the tail; the cacheable prefix survives | a code change (policy variant) + one pair |
| prefix-contiguous compaction | replace a mid-prefix run with a stub *in place*, so the prefix stays byte-stable up to the cut | a code change; the stub text itself changes the prefix, so measure it |
| stop paging | accept W8C's 2.11× and use the trace, not the pager | none — already recorded |

## 4. What is claimed, and what is not

- **Claimed:** on a read-once, growing request at a 24 k budget, the stable mode engages but cannot hold; the
  request is held at 0.25× of the control while cache-read falls to 0.22× and uncached input rises 1.90×; the
  artefact stays parsed-equal. That is a **negative** result for the design's cache-stability hypothesis on this
  workload, measured with the mode actually on — which the previous attempt could not say.
- **Not claimed:** any dollar figure (free tier reports `cost 0`, and the cache columns are harness-reported);
  any statement about a different workload, budget or provider; any claim that paging cannot help, only that
  *this* stability mechanism cannot recover the cache while evicting from the middle.
- Sampling: one pair, one model, one shape. Route length varied across runs of the same arm yesterday (41 vs 58
  calls on the control), so a single pair cannot separate an effect from noise — which is why the claim is about
  the mechanism (holds, prefix contiguity) rather than about a token ratio.

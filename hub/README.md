# hub/ — the hub.ctxvm.dev catalog (proof)

`06-odps-integration.md` §5: *"Catalog as code: public Git repo, `*.yaml` per
product, CI schema validation, static generation. hub.ctxvm.dev = Git repo +
ODPC + Actions. No bespoke hub server."*

This directory is the **T5 proof of that claim** — every artifact here is
generated by the open-data-products SDK itself and committed:

| File | What it is |
|---|---|
| `catalog.yaml` | ODPC v1.0 `kind: Catalog`, metadata `hub.ctxvm.dev`, one `productReferences` entry (ctxvm-corpus-0.1) → ODPS 4.1 |
| `index.html` | Standalone browser-viewable HTML catalog (same data) |

## Single-source-of-truth rule

The catalog references the root manifest directly:

```yaml
productModel:
  standard: ODPS
  version: '4.1'
  $ref: ../04-odps-dataproduct-corpus.yaml   # hub-relative
```

The manifest is NOT duplicated into hub/ — `hub.yaml`'s pointer is the
authoritative link, and `04-…yaml` remains the single source of truth
(it carries the SDK validation proof in its header).

## Regenerate (idempotent, byte-identical)

```sh
tools/build-hub.sh
```

The script: re-validates the root manifest → stages a copy → `odpc-build`
(catalog + HTML) → rewrites the $ref hub-relative → re-validates the committed
catalog with their SDK (`validate --json` → `valid:true`, `errors:[]`) →
`odpc-summary`. Two runs produce byte-identical output (SDK emits no timestamps).

## Deploy path (when hub.ctxvm.dev goes live)

GitHub Actions run of `tools/build-hub.sh` + publish `hub/` as Pages →
`hub.ctxvm.dev` serves the ODPC catalog + HTML. The manifest's `accessURL` /
`specsURL` claims (`/corpus/0.1/…`, `/llms.txt`) then map to handoff T5
successors; the references in hub/catalog.yaml stay resolvable because the hub
repo root IS this repo (single manifest at root).

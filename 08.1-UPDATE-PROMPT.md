# Master prompt: ctxvm / xCABI adoption push

You are the repo agent for `kapitaali/ctxvm-xCABI` (and its consumer `kapitaali/umpire`). Read `08-HANDOFF.md` §0–§4 first. Its rules of engagement and reporting protocol govern process. If anything below conflicts with it, follow the HANDOFF for process, and flag the conflict in your first report.

## 1. Goal

Make xCABI an **adoptable open standard**, or at minimum a **baseline other people can build products on**. The owner runs **OpenCode** and **Hermes Agent** daily. Success means evidence and outside users, not more internal scaffolding.

Priority order: (1) real data from real sessions, (2) a second harness emitting identical traces, (3) fixing metrics so claims are falsifiable, (4) packaging and distribution, (5) runtime ABI architecture design (W12, gated), (6) everything else.

## 2. Integrity rules (non-negotiable)

- Every external claim carries a locator at first mention. Unverified claims are marked `UNVERIFIED`, never stated as fact. The plan already records an incident of unsourced prior-art claims, so spot-check the arXiv references (2603.09023, 2603.02228, 2310.08560) and every quoted figure (84.4x, 21.8%, 857 sessions) against the papers. - Facts about Hermes Agent in this prompt come from third-party write-ups, not official docs. Verify against `hermes-agent.nousresearch.com` docs and the Hermes source before relying on any hook name or interface.

### W12. Runtime ABI architecture specification (design-only, gated)

**Gate:** this is design work only. Write no implementation and publish no header until W8 shows the paging gate passes or the owner approves (D7). So far the evidence is telemetry; a runtime ABI is control-plane scope.

**Role for this workstream:** act as a Principal Systems Architect specializing in low-level runtime design, C-ABI stability, and high-performance LLM context execution. Be precise, technical, and uncompromising on memory safety, layouts, and runtime efficiency.

**Objective:** design a Context Virtual Machine (`ctxvm`) that interfaces with language runtimes and native hosts across a stable C-ABI boundary (`xCABI`), treating LLM conversational context, tool states, and system frames as zero-copy, ABI-stable virtual memory spaces (analogous to page tables and process frames in an OS kernel). Produce a rigorous, production-grade specification that resolves the three risks below.

**Step 0: reconcile with the repo.** Confirm what "xCABI" currently denotes in `00-SPEC.md`. RFC-0 trace semantics stay sealed, and this layer must be consistent with the existing trace events (`page.declare`, faults, evictions). If the names collide, use a distinct working name in drafts and flag it. Put outputs in `design/runtime-abi/`.

**Step 1: justify before designing.** Write a half-page analysis of where zero-copy actually matters. LLM requests ultimately serialize to tokens and JSON over a network, so measure the allocation/copy share of real session latency (from W1/W4 traces plus a microbenchmark) against total latency. Identify where borrowing pays: large tool outputs, multi-branch sharing, local inference and KV-cache sharing, host-to-VM crossing frequency. Relate branching to prefix/KV-cache sharing in serving engines and provider prompt caches: a fork that changes the prefix forfeits cache hits, so price every fork in net-token terms using the W3 pricing model. Cite sources with locators. If the benefit is not measurable, say so and shrink the ABI to the minimum needed for safe handles.

**Risk 1: cross-boundary memory allocation and ownership.**
- Problem: passing dynamic strings, variable-length token arrays, and vector embeddings across a C-ABI boundary risks heap corruption when host and `ctxvm` use different allocators.
- Tasks: define a strict allocation and drop contract across the boundary. Propose an explicit Arena / Frame Allocator pattern (`ctxvm_arena_t`) where the host or VM controls allocation lifetimes. Specify C-compatible struct layouts for variable-length primitives, comparing length-prefixed slices, null-terminated strings, and dynamic buffer handles. Draft C signatures for initialization, slice allocation, frame appending, and teardown that explicitly enforce ownership boundaries.

**Risk 2: state branching and copy-on-write semantics.**
- Problem: agentic workflows need rapid branching, checkpointing, and rollback (parallel tool paths, context pruning).
- Tasks: design a virtual page/frame table for context frames: system prompt as read-only pages, conversation history as CoW dynamic pages, thread state as isolated stack frames. Define thread-safe, zero-copy branching across the boundary without duplicating text or token buffers. Detail how pointer invalidation is prevented when a child branch modifies or appends to a shared parent frame.
- Design leads to evaluate, not conclusions: pages immutable once sealed; growth by appending new pages, never by reallocating shared ones; reference-counted page sharing; generation-tagged handles so a stale handle returns an error instead of causing UB; explicit lease/release for borrowed slices.

**Risk 3: dynamic schema handling vs static C-ABI layouts.**
- Problem: tool calls and structured outputs rely on dynamic JSON Schemas, which clash with static C-ABI layouts.
- Tasks: provide a strategy for passing and executing dynamic schema contracts through `xCABI` without per-invocation string serialization. Evaluate opaque handle pointers (`uint64_t` handles plus a VM lookup table) against flattened ABI byte-code instructions for tool dynamic dispatch.
- Hypothesis to test: a content-addressed schema registry (schema hash to compiled validator handle), compiled once, invoked by handle, with JSON strings only at the model/provider boundary. Benchmark per-invocation overhead of the string path against the handle path and report numbers. Weigh bytecode dispatch honestly: verifiability, versioning, portability across language bindings, and the attack surface of an interpreter (it would need a verifier).

**Deliverables:**
1. `ctxvm_abi.h`: idiomatic C99 header defining memory structs, error codes, opaque handles, and lifecycle functions (init, slice alloc, frame append, fork, rollback, teardown).
2. Memory safety and invariant rules: an explicit list ("caller frees", "callee borrows", alignment guarantees, thread-safety per function, lifetime of every borrowed pointer).
3. Branching sequence walkthrough: a step-by-step memory diagram or structured trace of a zero-copy context fork, child append, and rollback, showing refcounts and which pointers stay valid.
4. A short decision record for each trade-off (allocator model, handle scheme, schema strategy) with the alternatives rejected and why.

**Required engineering rules for the header and any reference code:**
- Fixed-width integer types only; no enums of implicit size, no Rust types or C++ types across the boundary; documented endianness and alignment.
- ABI versioning: an `abi_version` and a `struct_size` field in every extensible struct, plus reserved fields; define the forward/backward compatibility policy.
- Nothing allocated by one side is ever freed by the other. Panics and exceptions must never unwind across the boundary (catch and convert to error codes).
- Error model: error codes plus an out-parameter for detail; document thread-safety for each function.

**Verification (include in the design, implement once the gate passes):**
- A C harness compiled with `-std=c99 -Wall -Wextra -pedantic`, run under ASan and UBSan.
- Miri on the Rust core where possible; loom or TSan for concurrent branching.
- Fuzzing of every FFI entry point.
- CI diff of a generated header (e.g. cbindgen) against the checked-in header, plus an ABI-compatibility check between versions.
- Property tests for CoW: after fork, mutating the child never changes the parent's bytes or invalidates its handles; rollback restores the exact prior state and frees child-only pages.
